## 1. 外層:標準 LZW

```
u32  解壓後長度(little-endian)
之後 LZW 位元流
```

LZW 的參數:

| 項目 | 值 |
|---|---|
| 打包方向 | **LSB-first**(先進來的位元在低位) |
| 碼寬 | 9 → 12 bit |
| 清表碼 | 256 |
| 結束碼 | 257 |
| 字典起點 | 258 |
| early change | **不做**(字典滿了才加寬,不提前一格) |

也就是 TIFF `LZWDecode` **不含** early-change 的那一版,等同 GIF 的變體。

四個參數任一個錯,症狀都不一樣,值得記下來當除錯線索:

- 打包方向錯 → 第一個碼就不是 256,通常立刻解出垃圾
- 起始碼寬錯 → 同上
- **early change 開了** → 前面幾百個位元組是對的,第二次加寬之後變雜訊
  ——這個最陰險,看起來像「繪圖有問題」不像「解壓有問題」
- 清表沒處理 → 大檔到中途爆掉,小檔完全正常

⇒ **解壓器一定要拿檔頭宣稱的長度當硬檢查**,不要讓它安靜回半截資料。
`Decompress()` 長度不符就報錯。

### 1.1 一條被推翻的舊記載

`docs/formats/01` 曾寫「`TILES.16` 不是標準 LZW(48 種參數組合最長只符 4 B)」。
**那是錯的** —— 而且錯在判準,不在參數。詳見該檔 §2.4。
一句話:當時拿「要等於 FM Towns 的位元組」當驗收,而中間還隔著色號順序那一層。

## 2. 內層:形狀表

`TILES.16` 是例外(解壓後就是 512 × 128 B 的裸 tile),其餘 50 個檔都是形狀表:

```
u16  N                              形狀數
N ×  { u16 圖位移, u16 遮罩位移 }     位移 0 = 這一格沒東西
每個 blob:
     u16 寬
     u16 高
     逐列像素
```

第一個 blob 的位移永遠等於 `2 + 4N` —— 表後面緊接著就是資料,中間沒有空隙。
這個性質可以當「N 讀對了沒」的即時檢查。

### 2.1 列的位元組數:三種深度三種規則

| 用途 | 深度 | 每列位元組 |
|---|---|---|
| EGA `.16` | 4bpp packed | `roundUp(w, 8) / 2` —— **補到 8 像素的倍數** |
| CGA `.4` | 2bpp packed | `ceil(w / 4)` —— **不補** |
| 遮罩 | 1bpp | `roundUp(w, 8) / 8` |

⚠ **EGA 補、CGA 不補**,這是最容易套錯的一條。證據來自 `CREATE.16` 的
51×67 那一張:

```
照 ceil(51/2) = 26 B 算 → 下一個形狀的位移差 134 B
照 roundUp(51,8)/2 = 28 B 算 → 正好接上
```

而同一張圖在 `CREATE.4` 裡要用 `ceil(51/4) = 13 B` 才對得上 —— 反過來補就垮。

EGA 補到 4 個位元組大概是因為原生模式是 4 個 bit-plane,一次寫 8 個像素。
但**資料本身是 packed 不是 planar**(見下)。

### 2.2 packed 不是 planar —— 這一條只能用眼睛定

24 px 寬時兩種佈局的列長剛好都是 12 B,**任何長度檢查都分不出來**。
是畫出來才確定的:

- packed → 一片有木紋的洞穴壁,邊緣是自然的曲線
- planar → 彩色直條雜訊

(`rulebook/64` 的「已知輸出當 oracle」:當靜態推導兩條路都自洽時,
拿人眼看得懂的輸出當裁判。)

### 2.3 遮罩的極性

原版 EGA 的疊圖是 `畫面 = (畫面 AND 遮罩) OR 圖`,所以

> **遮罩位元 1 = 保留背景 = 透明**

反過來解讀會把整隻怪物挖空,只留下背景。佐證:`MON0.16` 第 0 個形狀 24×66,
遮罩有 **749 個 1**,而圖裡色號 0 有 **1,083 個** —— 同一個數量級但不相等,
正是「大部分黑色是背景、少部分黑色是刻意畫的輪廓」該有的樣子。
若兩個數字完全相等,反而要懷疑遮罩只是「色號 0 的複製品」。

## 4. 驗收

```bash
tools/dev.sh go run ./cmd/u5dump pictures gamedata/DNG3.16 build/dng3.png
```

自動化(`picture_test.go`):

- `TestEveryPictureSetParses` —— 把所有 blob 的起點排序,**每個 blob 依
  寬 × 高 × 深度算出來的大小,必須正好等於它與下一個起點的距離**。
  50 個檔、398 個形狀一個不差。這條不需要看圖就能抓到列寬算錯。
- `TestDungeonPicturesHaveTheExpectedShape` —— 三個地牢圖組的形狀表一致。
- `TestDOSTilesMatchFMTowns`(在 `tiles_test.go`)—— 兩個平台的 tileset
  逐位元組相同。

目視:`u5dump pictures` 會把透明處填成洋紅,免得「遮罩極性反了」
看起來像「圖是空的」。

## 附:`MISCMAPS.DAT` —— 四間 11×11 的石室

與圖檔無關,但同屬「小到沒人替它寫規格」的那一類,一併記在這裡。

聖壇、寶典、黑棘的審問、王座廳這四幕都不在正常的場景地圖裡:原版把地點編號
設成 `0xFF`,再從這個檔載一張 11×11 蓋掉畫面。

| 位移 | 內容 | 誰載的 |
|---|---|---|
| 0x000 | 黑棘宮殿的地牢 | `sub_C414` |
| 0x0B0 | 八德聖壇 | `sub_1DA10`(腳下地形 25) |
| 0x160 | 終極智慧之寶典 | `sub_1DA10`(腳下地形 17) |
| 0x210 | 王座廳 | `sub_135FC` |

⚠ **列距是 16 不是 11。** 原版的搬運迴圈是
`byte_3F8F4[i*32 + j] = byte_3F844[i*16 + j]`(來源列距 16、目的列距 32),
所以一張佔 11 × 16 = 176 B,只有每列前 11 B 有意義。
照 11 讀的話第二列開始整張歪掉,而畫面看起來只是「有點亂」—— 不會有東西報錯。

★ 解出來的內容自己會說話,不需要另找 oracle:牢房那張有 `0xB9` 上鎖的門與
`0xBB` 上鎖的魔法門;寶典那張正中央是 `0x41`(那本書);王座廳有整排家具與
`0xAB`/`0xAC`/`0xAF` 的窗。而**站定的位置**((5,10) 往上走 7 步 → (5,3))
剛好讓那本書落在玩家正前方一格 —— 位移與步數兩邊獨立,對上了。

檔案 1,871 B,四張只用了前 704 B;後面還有東西,還沒查是什麼。
