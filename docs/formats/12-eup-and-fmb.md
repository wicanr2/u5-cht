## 1. `.EUP` 的整體佈局

```
0x0000  0x20   零(用途未追)
0x0020  8      曲名 ASCII("M1"、"M8"…)
0x0028  ...    小檔頭:0x31..0x34 有四個位元組會隨曲子變、0x4E..0x52 五個位元組
0x0254  0x120  8 byte 一組、重複到 0xFF 填滿(**每首不同**,用途未追)
0x0395  5      01 02 03 04 05(聲道編號?)
0x04D6  ...    ★ **固定音名表**:4 byte 一筆的 ASCII(" \0D-"、" \0D "、" \0E-"…)
0x07F6  8      簽章 "EUPHONY "
0x07FE  8      小檔頭(疑含速度 —— 見 §4)
0x0806  6×N    ★ **事件流**,每筆 6 byte,遇 status == 0xFF 結束
之後    ...     填充(四首都在檔尾前 0x2FC..0x300 就結束)
```

## 2. ★★★ 事件的欄位配置,以及它是怎麼被證明的

```
+0  status   高 nibble = 種類、低 nibble = 聲道
+1  step     ★ 距離**上一筆**的 tick 數(delta)
+2  gate     u16 LE —— 疑為音長,但 note-on 常常是 0
+4  data1    note-on 是音高;note-off **一律 0**;program change 是音色編號
+5  data2    note-on/off 是力度(絕大多數 0x40);program change 是 0xFF
```

| 種類 | 意義 |
|---|---|
| `0x9n` | note-on |
| `0x8n` | note-off(音高欄 0 ⇒ 收「該聲道當前那一個」) |
| `0xCn` | ★ **program change** —— `data1` 是 `FM_BANK.FMB` 的索引 |
| `0x00` / `0xF*` | 控制 / meta(每首固定 130 筆 `0x00`,用途未追) |

### 相位怎麼定的(不是猜的)

事件流的起點是 `簽章 + 16`。**證明方式是統計而不是註解**:

| 起點 | status 欄的樣子 | note-on / note-off |
|---|---|---|
| `sig + 0x40`(錯 2 個位元組) | 值域 0..120、高 nibble 完全散開 | 讀不出來 |
| **`sig + 16`** | 高 nibble **只有 8、9、0、F** | **881 / 882** |

★ **note-on 與 note-off 的筆數相等(差 0 或 1)** 是決定性的:相位錯的話
status 欄根本不是 status,這個關係不可能成立。十五首全部通過
(`TestEUPFieldLayoutIsProvenByNoteBalance`)。

⚠ 這一條取代「相信 u1-cht 的 `find_events` 相位掃描」—— 那支用「前 40 筆裡
有 38 筆的 byte0 落在 `0x8n/0x9n/0x00/0xFF/0xF2`」當判準,對 U5 的檔案
會停在錯的相位(實測 `sig+0x40`)。**同一個格式、同一個引擎,相位判準不通用。**

### program change 就在事件流開頭

M1 的前七筆:

```
c1 01 00 00 31 ff      ; 聲道 1 → 音色 0x31 = 49
c5 05 00 00 6f ff      ; 聲道 5 → 音色 0x6F = 111
c4 04 00 00 32 ff      ; 聲道 4 → 音色 0x32 = 50
c3 03 00 00 24 ff      ; 聲道 3 → 音色 0x24 = 36
c2 02 00 00 6e ff      ; 聲道 2 → 音色 0x6E = 110
c0 00 00 00 23 ff      ; 聲道 0 → 音色 0x23 = 35
f8 ff 00 00 5e 00      ; meta
92 02 00 00 29 40      ; ← 第一個真正的音
```

⇒ **六個聲道各選一個音色**,對得上 `U5_BGM.TBL` 的**六欄音量**(`docs/re/87` §1)。
十五首共 71 筆 program change。

## 3. `FM_BANK.FMB`:128 個帶名字的 FM 音色

```
0x0000  8      檔頭(M1 那份是八個空白)
0x0008  48×128 音色記錄
          +0x00  8   名字 ASCII("TRUMP1" "Horn" "Tuba" "FLUTE" "OBOE" "Piano"…)
          +0x08  40  ⬜ FM 參數,語意未定案
```

★ **8 + 128 × 48 = 6,152 = 檔案大小,整除無餘數** ⇒ 佈局定案。
而 EUP 的 program change 值域落在 0..127 ⇒ **兩份獨立資料互相佐證**。

名字在記錄開頭那 8 byte 也是可驗證的:位移偏一格就會讀到二進位參數,
名字立刻變亂碼(`TestFMBankVoicesHaveReadableNames` 順便釘住 `TRUMP1` /
`FLUTE` / `OBOE` 三個)。

### ⬜ 那 40 byte 為什麼不解釋

`TRUMP1` 的參數是:

```
01 01 02 02 | 18 11 00 00 | 10 10 15 15 | 0d 10 14 00 | 00 00 00 00
5f 40 0f 1f | 04 c0 00 00 | 00 00 00 00 | 00 00 00 00 | 00 00
```

兩個候選佈局:

- **(a) 10 參數 × 4 運算子(參數優先)**:讀成 MUL=`01 01 02 02`、
  TL=`18 11 00 00`、AR=`10 10 15 15`、DR=`0d 10 14 00`、SR=全 0、
  SL/RR=`5f 40 0f 1f`(高低 nibble)。**TL 前兩個有衰減、後兩個是 0**
  ⇒ 後兩個是載波,聽起來合理。
- **(b) 4 運算子 × 8 參數 + 8 共用(運算子優先)**:讀出來第三、四個運算子
  幾乎全 0,不合理。

⇒ (a) 看起來對,**但「看起來對」不是證據**。要定案得追驅動程式怎麼把它寫進
YM2612 的暫存器(`sub_34xxx` 那一族,走 FM Towns 音源驅動的 `AH=` 呼叫)。
在那之前這 40 byte **原樣保留不解釋** —— 猜錯會做出一個「聽起來像但不是原版
音色」的合成器,而那正是 `CLAUDE.md §3.0` 要避免的。

## 4. ⬜ tick → 秒還沒定案

十五首的累積 tick:M1 = 13,512、M2 = 8,213、M8 = 5,681、M152 = 6,362。

`../u1-cht/tools/render_eup_music.py` 用 **0.0108 s/tick**(≈ 48 ppqn @ 115 bpm),
換算 M1 ≈ 146 秒 —— 數量級合理,但那個常數是**從 U1 的曲長反推**的,不是讀出來的。

候選:`簽章 + 8` 那 8 byte 裡有兩個會隨曲子變(M1 `fc 2a`、M2 `fa 17`、
M8 `1c 11`、M152 `2c 13`),疑為速度。要定案得追誰讀它。
**不從長度反推**(`rulebook/62`)。
