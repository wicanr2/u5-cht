## 1. tile 點陣

| 項目 | 值 |
|---|---|
| tile 尺寸 | **16×16**,4bpp(每列 8 B,共 128 B) |
| tile 總數 | **512** |
| 佐證 | DOS `TILES.16` 檔頭前 4 B(u32LE)宣稱解壓後 **65,536 B** = 512 × 128 |

### 1.1 FM Towns `EGA0–EGA3.TIL`(未壓縮,目前的素材來源)

各 65,536 B = **128 tile × 512 B**;每個 tile 是原版 16×16 **機械放大 2 倍**後的
32×32 4bpp packed(每列 16 B × 32 列)。

還原成 16×16 時,水平取每 2 px 的第一個、垂直取每 2 列的第一列。
**解碼器同時驗證這個假設**:被丟掉的那一列必須與保留的相同、每個 byte 的高低 nibble
必須相同 —— 512 tile × 256 px 全數通過。不符就報錯,不安靜解出垃圾。

> 為什麼確定是 packed 而不是 EGA planar:檔內每個 byte 都是對稱 nibble(`0x22` `0xAA` …)。
> 在 4bpp packed 下這正好是「水平 2× 放大讓相鄰兩像素同色」;
> 而在 1bpp planar 下,2× 放大會讓 bit **成對**(`0b11001100`),`0x22 = 0b00100010` 不符。
> 另外實測 planar 解讀會得到 82% 黑 + 散落雜色,packed 則是規律的 EGA 抖色圖案。

### 1.2 色號:資料用 IGRB,不是 EGA 的 IRGB ⚠

**FM Towns** `EGA*.TIL` 的 4-bit 色號,**bit1 與 bit2 是對調的**
(那份 = IGRB,標準 EGA = IRGB)。DOS 的 `TILES.16` 本來就是 IRGB,不必換。

⇒ **換色號的地方在解碼器,不在算繪端**:`u5data.tileColorRemap` 在讀
`EGA*.TIL` 時就把每個像素換成標準 EGA 色號,所以解出來的 `Tile` 一律是 IRGB,
算繪直接用 `u5data.EGAPalette` 索引即可。

⚠ 此前這裡寫著「算繪一律用 `u5data.TilePalette`(已套 remap),不要直接用
`EGAPalette`」—— **`TilePalette` 這個符號從來不存在**,而 `EGAPalette` 正是
正確的那一個(它自己也對過 `DATA.OVL` 0x52EE 的 palette 表)。照那句話做會
編不過,或者把 remap 套第二次。`tools/check_doc_claims.py` 抓到的。

| tile 資料色號 | 標準 EGA 色號 | 顏色 | 出現在 |
|---|---|---|---|
| 1 / 9 | 1 / 9 | 藍 / 亮藍 | 水與波紋(互換下不變) |
| 7 / 8 | 7 / 8 | 淺灰 / 深灰 | 山(互換下不變) |
| 14 / 15 | 14 / 15 | 黃 / 白 | 建築(互換下不變) |
| **4** | **2** | **綠** | **草地(修正)** |
| **12** | **10** | **亮綠** | **森林高光(修正)** |

判定依據:單一變換(bit1↔bit2)同時修正所有錯的顏色、不動所有本來就對的顏色。
若改的是 palette 值本身,會連帶弄壞洋紅、棕、亮紅。
且該變換是**自反的**(做兩次回到原點),測試有固定住這個性質。

⚠ 仍屬語意推導;**最終核實要用 DOSBox 跑原版截圖比對**(P1 收尾項)。

## 2. 世界地圖

| 檔案 | 大小 | 內容 |
|---|---|---|
| `BRIT.DAT` | 52,480 B | 地表世界的 **205 個 16×16 chunk**(每 chunk 256 B) |
| `UNDER.DAT` | 65,536 B | 地底世界(256 chunk,不省略) |
| `DATA.OVL` @ **`0x3886`** | 256 B | **chunk 索引表**(16×16) |
| `TOWNE/CASTLE/KEEP/DWELLING.DAT` | 各 16,384 B | 場景地圖 |

世界地圖是 **256×256 tile = 16×16 個 chunk**。索引表每項對應一個 chunk 位置:

- 值 `0x00–0xCC`(0–204)= `BRIT.DAT` 裡第幾個 chunk
- 值 **`0xFF` = 該位置整塊都是水**(不存資料);共 51 個,`51 + 205 = 256` ✓

### 2.1 索引表位移是怎麼找到的

掃過整個 48,464 B 的 `DATA.OVL`,找「恰好 51 個 `0xFF`、其餘 205 個值互不重複且落在
0..204」的 256 B 區塊 —— **全檔只有一個命中**,就是 `0x3886`。
表要同時滿足「`0xFF` 個數 = 缺少的 chunk 數」與「非 `0xFF` 的值是 0..204 的一個排列」,
隨機資料撞出來的機率極低,這個唯一性本身就是證據。

⚠ 這個位移只對 **DOS 版** `DATA.OVL` 成立。FM Towns 的 `U5_E/` 沒有 `DATA.OVL`;
所以 API 設計成索引表由呼叫者提供,不把位移寫死進解碼流程。

### 2.2 已被推翻的假設(不要再重複)

~~`BRIT.OOL`(256 B)是 chunk 索引表,`0xFF` = 全水~~
→ 實測 `BRIT.OOL` 的值大多是 `0x00`、**一個 `0xFF` 都沒有**,不是索引表。它是什麼還沒查。

### 2.3 驗收

`u5dump world gamedata <U5_E 目錄> world.png` 產出 4096×4096 的完整地圖。
輪廓應該是 Britannia:C 形大陸環繞中央海灣、右上島群、右下 Serpent's Hold、左下島鏈。
顏色應該是藍海、綠地(深綠森林 / 亮綠草地)、灰山、右上棕色沙漠、城鎮的橘點。

自動化檢查(`map_test.go`):chunk 數 = 205、索引表全水位置 = 51、
水占全圖 30–75%、全圖用到 ≥ 50 種 tile。

## 2.4 更正:`TILES.16` 的壓縮就是標準 LZW

> 2026-08-07 下午。這一條原本寫在下面的「仍未解」裡,而且結論是錯的。

當初的記載是「**不是**標準 LZW(48 種參數組合最長只符 4 B)」。實際上
LSB-first、9→12 bit、不做 early change 的那一組**一開始就是對的** ——
它一路解出完整的 65,536 B,長度與檔頭宣稱的分毫不差。

錯在**驗收條件本身有洞**:當時拿「解出來的位元組要等於 FM Towns 的
`EGA*.TIL`」當判準,而兩者中間還隔著一層色號順序(`tileColorRemap`)。
於是正確的解壓器在第 5 個位元組就被判定失敗,而它其實只是顏色編號不同、
圖形完全一樣。

**教訓**:「A 應該等於 B」這種驗收,在下「A 錯了」的結論之前,要先問
「A 與 B 之間是不是還隔著一層我沒算進去的轉換」。48 組參數全掃過卻全滅,
本身就是「判準有問題」的訊號 —— 一個真的錯的假設通常會有某幾組**比較接近**。

修好判準之後的驗收是決定性的:

```
DOS TILES.16 解壓的 65,536 B
  ==  FM Towns 四個 EGA*.TIL 降回 16×16、套色號 remap、壓回 4bpp
```

**逐位元組完全相同**(`TestDOSTilesMatchFMTowns`)。順帶把色號 remap 從
「語意推導」升級成「兩份獨立資料量出來的差」,並確認 **DOS 的色號本來就是
標準 EGA**。
