> 輸入檔:`WORRIORS.EXP`(FM Towns)、`DUNGEON.DAT`、`DUNGEON.CBT`、DOS `DATA.OVL`
> 日期:2026-08-07

---

## 1. `DUNGEON.DAT` = 8 座 × 8 層 × 8×8

載入的算式直接寫在 `sub_2D564`:

```asm
mov  eax, edi
shl  eax, 9              ; 地點 × 512
sub  eax, 4000h
push eax                 ; 檔案位移
push 200h                ; 512 B
push offset dword_3E16C
push offset aDungeonDat  ; "DUNGEON.DAT"
call sub_2C740
lea  eax, [edi+1]
mov  byte_3E0A3, al      ; 地點 = 索引 + 1
```

一次只讀 **512 B** = 一座地牢的八層。`地點 × 512 − 0x4000` 代表索引 0x20
對應檔案位移 0,而進去之後 `byte_3E0A3 = 索引 + 1` —— 所以**八座地牢的
地點編號是 0x21..0x28**。這正好對得上咒語場合表的「0x21..0x7F 算地牢」
(`docs/re/17`)與上下船的「`0x20 < 地點 < 0x29` 一律 Not here!」(`docs/re/11`)。

層內定址全檔一致:

```asm
movzx eax, byte_3E0A5    ; 樓層
shl   eax, 6             ; × 64
lea   eax, dword_3E16C[eax+edx*8]
mov   bl, [eax+ecx]      ; [樓層*64 + y*8 + x]
```

⇒ 一層 64 B、row stride 8 → **8×8**。4096 / 64 = 64 層 = 8 座 × 8 層。

## 2. 格子語意:高四位元是種類

| 高位元 | 意義 | 依據 |
|---|---|---|
| `0x00` | **通道**(可走) | 繪圖 `sub_F35C` case 0 什麼都不畫 |
| `0x10` | 上行梯 | `sub_417C` 的 Klimb-U |
| `0x20` | 下行梯 | `sub_417C` 的 Klimb-D |
| `0x30` | 上下皆可 | 同上,兩邊都比 |
| `0x40` | 寶箱 | |
| `0x50` | 噴泉 | `sub_CE78` 印「a gurgling fountain!」 |
| `0x60` | 陷阱 | `sub_5150` 依完整位元組分派 |
| `0x70` | **開過的寶箱** | ⚠ 原本照「怪物走得過去」猜成門,`sub_18D18` 的 `(tile & 8) \| 0x70` 推翻了(見 `docs/re/21`) |
| `0x80` | 魔法陷阱 | `sub_5150` |
| `0xA0` | **房間** | `sub_5150` 的 `cmp al, 0A0h` |
| `0xB0` | 牆 | 繪圖 case 11 畫實心塊 |
| `0xC0` / `0xD0` / `0xE0` | 未定,一律當牆 | |
| `0xF0` | **房間** | `sub_5150` 的 `cmp al, 0F0h` |

⚠ **0x00 是通道不是牆。** 直覺會覺得「0 = 沒東西 = 實心岩」,但 0xB0 在全檔
出現 1926 次、0x00 出現 1199 次,而怪物移動那段放行的正是 `< 0xA0`
(排除 0x60 與 0x80)—— 0x00 在裡面、0xB0 不在。認反了整張圖會變成負片。

### 完整位元組才分得出來的幾個

`sub_5150` 對陷阱是比**整個位元組**,不是高四位元:

| 值 | 效果 |
|---|---|
| `0x61` / `0x69` | **陷阱坑** —— 掉下一層(`sub_4EB8`) |
| `0x62` / `0x6A` | **炸彈**「Bomb Trap! KABOOM!!」,全隊受傷 |
| `0x80` / `0x88` | **睡眠法術**(`sub_4DC8` 印「Sleep spell!」) |
| `0x81` / `0x89` | **毒**(`sub_4E58` 印「Poison!」) |
| `0x82` / `0x8A` | **烈焰**,全隊受傷 |
| `0x83` / `0x8B` | **防護力場 —— 什麼都不會發生**(跳表送進 default) |

⚠⚠ **更正(第四輪)**:此前記載「`0x80` / `0x89` 是睡眠」是錯的。
`jpt_52C7` 是一張索引 = `格子 − 0x81` 的 **10 格**跳表,逐格數下來是
`0x80`/`0x88` 睡眠、`0x81`/`0x89` 毒、`0x82`/`0x8A` 烈焰,其餘 default。
錯因是憑「0x80 系列 = 睡眠」的印象往下填,**跳表沒有整張抄完**。

而 `0x80..0x83` 這一組不只是地圖上本來就有的陷阱 —— 它同時是**四個 `*Grav`
咒語放出來的力場**(`sub_18A08` 的 `byte_55E24` = `82 81 80 83`)。
玩家放的與地圖上的走同一段程式碼,所以是同一組編號。詳見 `docs/re/17` §9.1。

睡眠與毒**不是全隊一律中**:`sub_4DC8` / `sub_4E58` 逐人擲 `random(1,30)`,
敏捷大於點數就躲掉,狀態已是 `'D'` 的跳過。

### 位元 3 = 頭上有洞

掉進陷阱坑之後 `sub_4EB8` 做兩件事:把原本那一格 `and 0xF8`(陷阱用掉了)、
對落點 `or 8`。而 `sub_417C` 的 Klimb 往上就是看這一位元 —— 外加
`byte_3DFBB`(疑為繩索,存檔位移還沒對出來,所以引擎先一律當成沒有)。

炸彈觸發後那一格被清成 `& 8` —— **只留這一位元**,其餘全清。

## 3. 進出

`sub_2D564` 一開頭就是一段線性搜尋:

```asm
mov  edi, 20h            ; ★ 從 0x20 開始
loc:
cmp  edi, 28h            ; ★ 掃到 0x27
jge  ...
mov  al, byte_410F4[edi] ; 地點表的 X
cmp  al, byte_3E0A6
```

⇒ **地點表其實有 40 筆,不是 32。** `docs/re/03` 只 dump 了前 32 筆
(城鎮與城堡),後 8 筆就是地牢入口,三張平行表(`off_41054` 名稱 /
`byte_410F4` X / `byte_4111C` Y)是同一組:

```
32 DECEIT   (240, 73)    36 COVETOUS (156, 27)
33 DESPISE  ( 91, 67)    37 SHAME    ( 58,102)
34 DESTARD  ( 72,168)    38 HYTHLOTH (239,240)
35 WRONG    (126, 20)    39 DOOM     (128,128)
```

Doom 在 (128,128) —— 世界地圖正中央,也就是地底世界的入口。

其他規則:

- **得下來走路**才進得去(`cmp byte_3E08C, 1Ch`,否則印「On foot!」)。
- 落點是第 1 層的 **(1,1)**;從地底世界鑽上來則是第 8 層的 (7,7)
  —— 唯一的例外是 Doom(地點 0x28),它從下面進去也走地面那條。
- Doom 還有一道額外門檻:`byte_3E0D8 & 3E0D9 & 3E0DA` 三個都 ≥ 0x80
  才進得去,否則印「Attacked at entrance!」直接開打。那三個位元組是什麼
  **還沒追到**,所以這條沒實作。

### 入口那一格長什麼樣(實測全部八座)

```
DECEIT   0x10    DESPISE 0x10    DESTARD  0x08    WRONG 0x10
COVETOUS 0x10    SHAME   0xF0    HYTHLOTH 0x30    DOOM  0xF0
```

五座是上行梯、Destard 是一個**頭上的洞**(要繩索)、Shame 與 Doom 的入口
**直接就是房間** —— 一進去就開打。

我第一版把驗收寫成「第 1 層一定有上行梯」,三座一起紅。斷言寫太死。

## 4. 房間(`DUNGEON.CBT`)

`sub_42CC` 的位移算式:

```
房號     = tile & 0x0F
地牢索引 = 地點 − 0x21;★ 索引 ≥ 1 的再減一
位移     = 地牢索引 × 11 × 512 + 房號 × 11 × 32
         = 地牢索引 × 5632 + 房號 × 352
```

一間房 **352 B —— 與地表的戰鬥地圖完全相同的格式**,所以引擎直接沿用
`CombatMap`,房間就是一場戰鬥。一座地牢 16 間 = 5632 B,
而檔案 39424 B = **7 個區塊**配 8 座地牢:`if (idx >= 1) idx--` 讓
**前兩座共用同一批房間**。這是原版的算式,照抄。

### 房間裡的怪物在偏移 171

`sub_FE48` 在**隨機遭遇**那條路徑上寫 `byte_3F99F[槽] = 生物*4 + 0x40`,
而 `0x3F99F − 0x3F8F4 = 171` = 第 5 列 +11。地牢房間則是從檔案讀同一段
—— 兩條路徑共用同一個 16 B 陣列。

實測 112 間房裡 **108 間有怪物**;那 16 B 裡 986 個是合法生物編號
(4 的倍數 + 0x40),另外 353 個是小值(1..15、30、31)與 235/237/238/239,
看起來是**房間裡的物件**(寶箱之類)—— 那部分還沒解,引擎只取生物。

同一段程式碼也證實了 `byte_3F056`(怪物屬性 +6)就是**隻數上限**:
隨機遭遇擲 `random(1, 上限)`,而 8 / 16 直接用不擲 —— 與 `docs/re/16`
從 `sub_2F0EC` 得到的結論一字不差,兩處互相印證。

## 5. Uus Por / Des Por 的一段死碼

`sub_3F34(±1)` → `sub_3ED0(目標層, 1)`:

```asm
and edi, edi
jnz short loc_3F29      ; ← tile != 0 就失敗
cmp edi, 0E0h           ;   以下四個 cmp 永遠到不了
jz  short loc_3F29
cmp edi, 0D0h
jz  short loc_3F29
cmp edi, 0C0h
jz  short loc_3F29
cmp edi, 0B0h
jnz short loc_3F2B
```

原始碼大概是 `if (t == 0 || t == 0xE0 || t == 0xD0 || t == 0xC0 || t == 0xB0)
return 0;` —— 第一個條件一成立,後面四個永遠不會被測。實際效果是
**目的地那一格必須是純通道(高四位元 0)**,比作者看起來想要的還嚴。

引擎照抄實際行為,不照抄意圖。

## 7. 第一人稱透視:幾何、選圖、以及三條被推翻的規則(2026-08-07 第二輪)

> 輸入檔:`WORRIORS.EXP`(FM Towns)+ `gamedata/DNG1-3.16`
> 這一輪能做,是因為 `.16` 的 LZW 壓縮先破了(`docs/formats/03`)。

### 7.1 繪圖流程(`sub_3D14`)

```
若光明計時器與火把計時器**都是 0** → 畫一個黑框就結束
   (地牢裡沒火把是真的什麼都看不到,不是「暗一點」)

x, y = 隊伍座標
for depth = 0..3:
    if !sub_36C0(x, y, depth): break     ; 這一格擋不擋視線(擋住就在裡面畫正面)
    if depth == 0 且腳下是 0xE0(門口): 跳過側牆
    sub_3878(x + 側向, y + 側向, 0, depth)   ; 左
    sub_3878(x − 側向, y − 側向, 1, depth)   ; 右
    x += 前向; y += 前向
```

⚠ **深度 0 是腳下這一格,不是前面那一格。** 認錯會整個往前偏一格,
而畫面看起來仍然像走廊,不會當場穿幫。

側向來自 `byte_4FFA4` / `byte_4FFA8`(= 朝向轉 90 度);
前向來自 `word_41970` / `word_41978`(北 / 東 / 南 / 西 = `(0,−1) (1,0) (0,1) (−1,0)`)。

### 7.2 選哪一張圖

側牆(`sub_3878`,看**側邊那一格**):

| 側邊的格子 | 形狀 |
|---|---|
| `< 0xA0`(通道類) | `16 + d` 看得穿的開口 |
| `0xA0` / `0xE0` / `0xF0` | `4 + d` 側牆上有門 |
| `0xC0` | `20 + d` |
| `0xB0` / `0xD0` | `0 + d` 實心側牆 |

正面(`sub_36C0`,查 `byte_4FEEE[種類]`):

| 擋住視線的格子 | 形狀 |
|---|---|
| `0xB0` / `0xD0` | `8 + d` |
| `0xA0` / `0xE0` / `0xF0` | `12 + d` |
| `0xC0` | `24 + d` |
| **深度 0** | **一律 12**(`if (depth == 0) shape = 0x0C`) |

⇒ `DNG*.16` 的 28 格裡第 **8** 與第 **24** 格是空的,不是漏做:
深度 0 永遠走 12,那兩個基底的第 0 階從來沒人要。

### 7.3 畫在哪裡 —— 切片寬度自己把答案講完了

FM Towns 的座標表是它自己 640×480 的版面,套不到 DOS。但 DOS 的切片寬度:

```
側牆四階  24 + 32 + 16 + 8 = 80
正面四階  80 / 56 / 24 / 8
```

**80 就是半個畫面**,而正面第 d 階的寬度**正好等於 80 減掉前面每一階側牆的寬度**:

```
80 − 0 = 80 ✓   80 − 24 = 56 ✓   80 − 24 − 32 = 24 ✓   80 − 24 − 32 − 16 = 8 ✓
```

四條同時成立,而且兩組數字來自檔案裡兩批**不同的形狀**。這不是湊出來的。
每張切片是**半邊**,右半水平鏡射 → 整個視野 **160 × 164**。

組出來的畫面確實是一條對稱的透視走廊(先在 Python 裡合成三個場景目視確認,
再落成 `internal/u5data/dungeonview.go`)。

⚠ 側牆第 0 階只有 24 px、第 1 階反而 32 px —— 不是打錯。深度 0 是**腳下**這一格,
它的側牆就在身邊、只露出畫面邊緣一條;前面那一格才是視覺上最大的一面。

### 7.4 外觀分三套(`sub_5378`)

`n = 地點 − 0x20`:

```
n == 1, 4, 5  → DNG3 磚牆   欺瞞 / 謬誤 / 貪婪
n == 6, 7     → DNG2 熔岩   羞恥 / 海斯洛斯
其餘          → DNG1 洞穴   輕蔑 / 毀滅 / 末日
```

⚠ **不是「第 n 座用第 n 套」。** 引擎第一版拿索引對 3 取餘數,欺瞞就變成洞穴了。

### 7.5 三條被推翻的規則(都是真的機制,不只是畫面)

**(a) `0xE0` 是門口,不是「語意未定的牆」**

`sub_48F4` 在左轉與右轉前檢查 `目前這一格 & 0xF0 == 0xE0`,成立就印
**「Not in doorway!」**擋下來 —— 門框太窄轉不了身。**轉身 180 度不受這條限制**
(走的是 default case)。而且門口是**走得過去的**(見下)。

**(b) 阻擋規則**

```
前進:0xA0 < kind < 0xE0 擋下  → 只有 0xB0、0xC0、0xD0
後退:再加上 0xA0 與 0xF0(房間)
```

也就是:**房間可以走進去,但不能倒退進去**。漏掉後半條的話玩家可以倒著走進戰鬥。
引擎原本把 `0xE0` 也算成牆 —— 那讓所有門口都變成死路。

**(c) 座標是環繞的**

`if (v < 0) v = 7; if (v > 7) v = 0` —— 8×8 是個環面,走出東邊從西邊出來。
引擎原本在邊界印「Blocked!」,把地牢變成有牆的盒子。

**(d) `0x83` 是電擊力場,而且它不在踩踏分派表裡**

`sub_48F4` 在移動時攔下 `tile == 0x83`,呼叫 `sub_4834`:
印「Ouch!」「Electric field!」、畫面閃白、全隊受傷(`sub_2A4D0`)、
**把人彈回原格**。所以玩家從來沒有真的站上去過 ——
`jpt_52C7`(踩踏分派)當然看不到它,而 §9.1 一度因此把它記成「無效果的防護力場」。

> **一個效果沒出現在你正在讀的那張表裡,先想想它是不是在另一條路徑上。**

它同時是 In Sanct Grav 放出來的力場(`byte_55E24[3] = 0x83`)——
U5 手冊裡那個咒語就叫 Energy Field,對得上。

  形狀編號是 `2 × 深度 + 基底`。表已 dump,還沒接。

  依外觀主題有特別處理)。
- 噴泉的動畫(`sub_39A8` + `byte_4FFA0` 三格循環)與力場動畫(`sub_33F0`)。
