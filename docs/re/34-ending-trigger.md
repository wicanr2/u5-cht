## 1. 已經確定的鏈

結局那一幕(`sub_135FC`)在整個執行檔裡**只有兩個呼叫點**,而且兩個都
守著同一個條件:

```
sub_42CC   (戰鬥)     … cmp byte_3E0B0, 4Dh ; jnz …  → call sub_135FC
sub_163B0  (戰鬥收尾) … cmp byte_3E0B0, 4Dh ; jnz …  → call sub_135FC
```

`0x4D` 是 `'M'`。所以問題收斂成:**誰把 `byte_3E0B0` 設成 `'M'`?**

全檔只有一處(`sub_161E4`):

```
i = byte_3E0AE                        // 目前處理到的單位 / 投射物索引
p = &dword_3EF50[i*8]
if (p[2] == 0)          return;
if (p[2] & 0x20)        return;
if (p[7] != 2)          return;       // ← 未知 A:型別 2 是什麼
t = byte_3F854[p[6]]
if ((t & 0xFC) != 0x3C) return;       // ← 未知 B:0x3C..0x3F 這一組
byte_3E0B0 = 'M';
印 "<某某> is absorbed!"
```

也就是說:**某個「型別 2」的東西落在某一組地形上,被「吸收」掉,遊戲就結束。**

---

## 2. 型別 2 從哪來(部分)

`dword_3EF50` 這張表的 `+7` 全檔只有一處寫入 2 —— 在 `sub_163B0`
(戰鬥收尾)裡,而且對象是**物件表** `dword_3E46C`,不是同一張表:

```
if (byte_3E0B3 != 0 && (物件[i].種類 & 0xFC) == 0x2C) {
    物件[i].種類 -= 8;                 // 0x2C..0x2F → 0x24..0x27
    物件[i].tile -= 8;
    物件[i][+5] = 0x63;                // 99
    物件[i][+7] = 2;                   // ← 型別 2
} else {
    物件[i] 整槽清空
}
```

兩張表的 `+7` 是不是同一個欄位還沒確認 —— `dword_3EF50` 與 `dword_3E46C`
是不同位址,只是**槽的大小都是 8 B**。在確認之前不能把兩邊接起來。

---

## 3. 未知 A 解掉了:那是戰場單位表

`docs/re/16` §1 早就把它解出來了 —— 我只是沒回去查(這正是
`00-function-index.md` 存在的理由):

```
dword_3EF50   32 槽 × 8 B,0..5 是隊員、6..31 是敵人
  +2  旗標(0x20 = 死亡)
  +6  戰場 X
  +7  戰場 Y
```

所以 `sub_161E4` 的條件其實是**位置**,不是型別:

```
單位還活著(旗標非 0 且沒有 0x20)
而且 戰場 Y == 2
而且 byte_3F854[戰場 X] 的高六位是 0x3C
```

§2 那段「型別 2」的解讀是錯的 —— `sub_163B0` 寫的 `[ebx+7] = 2` 是
**物件表**的欄位,與戰場單位表的 `+7` 只是碰巧同一個位移。
兩張表不同,不能對接。

## 4. 未知 B:掃過三處都沒有,而且正對照說它不是地形

`byte_3F854[戰場X]` 取出來的值,高六位要等於 0x3C。若那是地形碼,
就該找得到一張含 0x3C..0x3F 的地圖。**三處全掃,零命中**:

| 掃過的地方 | 結果 |
|---|---|
| `DUNGEON.CBT` 112 張戰鬥地圖的 11×11 | 0 |
| `BRIT.CBT` 16 張 | 0 |
| `MISCMAPS.DAT` 四間石室的 11×11 | 0 |

⚠ 空結果不能直接當結論(`diagnosis-notes/02`:先做正對照)。
於是掃全部 `.DAT` / `.CBT` 看這四個位元組值到底出現在哪:

```
SHOPPE.DAT    49    QUESTION.DAT  28    LOOK2.DAT      5
BRIT.DAT       7    END.DAT        3    MISCMSG.DAT    3
ENDMSG.DAT     2    MISCMAPS.DAT   1    STORY.DAT      1    DUNGEON.CBT 1
```

★ **命中幾乎全在文字檔** —— 0x3C..0x3F 就是 ASCII 的 `< = > ?`。
真正的地圖資料裡(`BRIT.DAT` 52 KB 裡 7 次、`DUNGEON.CBT` 39 KB 裡 1 次)
是雜訊等級。

⇒ **地形碼 0x3C..0x3F 在整個遊戲裡幾乎不存在**,所以
`byte_3F854[戰場X]` **不是地形查表**。目視切出來的「白色城垛 / 城門拱門」
是 tileset 裡確實畫了、但地圖上不用的格子。

`byte_3F854` 是什麼還沒定:它落在 `byte_3F844`(石室搬運暫存,11×16 = 176 B,
IDA 把它切成 `byte_3F844` 16 B + `byte_3F854` 160 B 兩個符號)裡的第 1 列 ——
但 Y 的條件是 2 不是 1,對不起來。也可能整塊在戰鬥期間被別的東西借用了。
