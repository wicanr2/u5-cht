## 1. 已經確定的鏈

結局那一幕(`sub_135FC`)在整個執行檔裡**只有兩個呼叫點**,而且兩個都
守著同一個條件:

```
sub_42CC   (戰鬥)     … cmp byte_3E0B0, 4Dh ; jnz …  → call sub_135FC
sub_163B0  (戰鬥收尾) … cmp byte_3E0B0, 4Dh ; jnz …  → call sub_135FC
```

`0x4D` 是 `'M'`。所以問題收斂成:**誰把 `byte_3E0B0` 設成 `'M'`?**

全檔只有一處(`sub_161E4`):

```
i = byte_3E0AE                        // 目前處理到的單位 / 投射物索引
p = &dword_3EF50[i*8]
if (p[2] == 0)          return;
if (p[2] & 0x20)        return;
if (p[7] != 2)          return;       // ← 未知 A:型別 2 是什麼
t = byte_3F854[p[6]]
if ((t & 0xFC) != 0x3C) return;       // ← 未知 B:0x3C..0x3F 這一組
byte_3E0B0 = 'M';
印 "<某某> is absorbed!"
```

也就是說:**某個「型別 2」的東西落在某一組地形上,被「吸收」掉,遊戲就結束。**

## 2. 型別 2 從哪來(部分)

`dword_3EF50` 這張表的 `+7` 全檔只有一處寫入 2 —— 在 `sub_163B0`
(戰鬥收尾)裡,而且對象是**物件表** `dword_3E46C`,不是同一張表:

```
if (byte_3E0B3 != 0 && (物件[i].種類 & 0xFC) == 0x2C) {
    物件[i].種類 -= 8;                 // 0x2C..0x2F → 0x24..0x27
    物件[i].tile -= 8;
    物件[i][+5] = 0x63;                // 99
    物件[i][+7] = 2;                   // ← 型別 2
} else {
    物件[i] 整槽清空
}
```

兩張表的 `+7` 是不是同一個欄位還沒確認 —— `dword_3EF50` 與 `dword_3E46C`
是不同位址,只是**槽的大小都是 8 B**。在確認之前不能把兩邊接起來。

## 3. 兩個未知

**未知 A:`dword_3EF50` 是什麼表、`+7 == 2` 代表什麼。**
`sub_A360`(唯一呼叫 `sub_161E4` 的地方)一開頭也是
`esi = &dword_3EF50[byte_3E0AE*8]`,看起來是逐單位處理的迴圈。
但這張表與物件表的關係還沒釐清。

**未知 B:地形 0x3C..0x3F 是什麼。**
從 tileset 切出來目視:0x3C 與 0x3F 是**白色城垛**、0x3D 是爬滿藤蔓的牆、
0x3E 是**城門拱門**。四個都是城堡外牆的一部分 —— 對「戰鬥中的單位站上去」
這個語境講不通,所以 `byte_3F854[p[6]]` 大概**不是地圖地形**。

`byte_3F854` 的位置本身是個線索:`byte_3F844` 是石室的搬運暫存區
(列距 16,見 `docs/re/27`),`0x3F854 = 0x3F844 + 0x10` 正好是它的**第二列**。
兩者是不是同一塊緩衝還沒查。
