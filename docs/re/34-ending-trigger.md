## 1. 鏈

結局那一幕(`sub_135FC`)在整個執行檔裡只有兩個呼叫點,兩個都守著同一個條件:

```
sub_42CC   (戰鬥)     … cmp byte_3E0B0, 4Dh ; jnz …  → call sub_135FC
sub_163B0  (戰鬥收尾) … cmp byte_3E0B0, 4Dh ; jnz …  → call sub_135FC
```

`sub_135FC` 讀 `MISCMAPS.DAT` 位移 0x210(王座廳那張石室)與 `ENDMSG.DAT`,
印 "… lives!" / "Yes" / "No" / "He says" / "I see…" —— 確定是結局。

`0x4D` 是 `'M'`。問題收斂成:**誰把 `byte_3E0B0` 設成 `'M'`?**

---

## 2. 先更正兩個讀錯的東西

這一份的第一版有兩處讀錯,而且兩處都導向「這個條件大概永遠不成立」的結論。
兩處都不是讀得不夠仔細,是**沒去查那個符號到底是什麼**。

### 2.1 `byte_3E0B0` 不是「結局旗標」,是撤離方向

第一版寫「全檔只有一處寫它」。那句話只對**字面量 `'M'`** 成立 ——
`mov byte_3E0B0, al`(寫一個算出來的值)另有三處:

| 位置 | 是什麼 |
|---|---|
| `sub_27D24` | **存檔載入**,逐欄位 fgetc 的其中一格 → 它是存檔欄位 |
| `sub_2F0EC` | `sub eax, eax` 之後寫入 → 清成 0 |
| **`sub_15E20`** | ★ 真正的用途 |

`sub_15E20` 是**戰鬥撤離**:

```
if ((byte_3E08C & 0xF8) == 0x20) { 印 "Stay with ship!"; return 0 }
if (單位旗標 & 0x80) {
    if (byte_3E0B0 == 0)  byte_3E0B0 = 方向          // 第一個逃的人決定出口
    else if (方向 != byte_3E0B0 && (byte_3E0B1 & 0x80))
        印 "All must use the same exit!"; return 0
}
… 印 "Leave" 或 "Escape",離開戰場
```

方向由 `sub_15F18` 的跳表給,值是 1..4(西 / 東 / 北 / 南)。

⇒ **`byte_3E0B0` 是「這場戰鬥大家從哪一邊撤」。**
`'M'` 是塞進同一格的**哨兵值** —— 一個不可能是方向的數字,
用來告訴戰鬥收尾「這場不是打完的,是被吸走的」。

### 2.2 `byte_3F854` 不是腳下那一格,是**正北**那一格

第一版把 `byte_3F854[戰場X]` 讀成「單位站的地形」,查不到對應的地圖資料,
於是推論「這個條件永遠不成立」。

真相在 `miscmap.go` 早就寫過的一句話上:**`byte_3F844` 是 11×11、列距 16 的
戰場 / 石室暫存**。三處獨立佐證:

```
sub_C414   byte_3F8F4[i*32 + j] = byte_3F844[i*16 + j]      i,j ∈ 0..10
sub_135FC  同一段搬運迴圈,一字不差
sub_295AC  byte_3F844[y*16 + x] = 地形                       執行期寫入
```

而 `0x3F854 − 0x3F844 = 0x10 = 16` = **一列**。所以

```
byte_3F854[X]  ==  byte_3F844[1*16 + X]  ==  戰場 (X, 1)
```

`sub_161E4` 要求單位的戰場 Y == 2,查的卻是第 1 列 ——
**它看的是單位正北那一格。**

## 3. 條件

```
sub_161E4:
    單位 = dword_3EF50[byte_3E0AE]        // 這一回合行動的那個
    if (旗標 == 0)        return          // 空槽
    if (旗標 & 0x20)      return          // 已死
    if (戰場 Y != 2)      return
    if ((戰場[X][1] & 0xFC) != 0x3C) return
    byte_3E0B0 = 'M'
    印 "<某某> is absorbed!"
```

呼叫點只有一個:`sub_A360`(戰鬥迴圈)在每個單位行動完之後。

`dword_3EF50` 的 +6 / +7 是戰場 X / Y —— 這一點由 `sub_15F18` 獨立確認:
它把 `+6` 加上東西向的增量、`+7` 加上南北向的增量。

## 4. 0x3C..0x3F 是城堡

把這四格從 tileset 切出來看(`build` 一次就好,不必入庫):
**白色城垛與黃色拱門** —— 城堡的外牆與城門。

而它們在**世界地圖**上只出現七格,全部圍著兩座城堡的入口:

| 座標 | 地形 | 誰 |
|---|---|---|
| (87,106) (85,107) (86,107) (87,107) | 3C 3D 3E 3F | 不列顛王的城堡(地點 17,(86,107)) |
| (197,244) (195,245) (197,245) | 3C 3D 3F | 黑棘的宮殿(地點 18,(196,245)) |

(用 `DATA.OVL` 0x3886 的 chunk 索引表把 `BRIT.DAT` 組成 256×256 之後掃的,
不是拿檔案位移硬換 —— `BRIT.DAT` 只存 205 個非全水 chunk。)

⇒ **條件是:在戰場第 2 列站著,正北是城堡的牆或門,就會被「吸收」,
而戰鬥收尾播結局。**

## 5. 第一版的結論被推翻了

第一版寫:

> **假設(未驗證):以出貨的資料而言,這個條件永遠不成立。**

那是建立在「`byte_3F854` 是腳下地形」之上的。改成「正北那一格」之後,
掃描的結果仍然是「固定戰場地圖裡沒有城堡地形」——

| 掃過的地方 | 0x3C..0x3F |
|---|---|
| `BRIT.CBT` 16 張 | **0** |
| `DUNGEON.CBT` 112 張 | 1(第 111 張的中繼資料區,不在 11×11 格子裡) |
| `MISCMAPS.DAT` 四間石室 | **0**(檔案裡唯一一次在 0x5A1,四張石室結束於 0x2C0 之後) |
| **`BRIT.DAT` 世界地圖** | **7 —— 就是上面兩座城堡** |

但**結論不同了**:戰場不是只能來自 `.CBT`。`sub_295AC` 會在執行期
把地形寫進 `byte_3F844`(它先呼叫 `sub_DB10` 去查當前地圖那一格),
也就是原版**用周遭地形當場組戰場**的那條路。在城堡門口開打,
城牆就會進到戰場裡。

⇒ **條件是搆得到的**,只是要走那條路。第一版的「永遠不成立」撤回。

## 6. 實作到哪裡

`checkAbsorbed()` 照 §3 寫好了,掛在每個單位行動完之後(同原版的呼叫點),
三條測試釘住:觸發、**只看正北不看腳下**、四個地形碼的邊界。

⬜ **還缺的一段**:本引擎的戰場地形目前全部來自 `BRIT.CBT` / `DUNGEON.CBT`
的固定地圖,而那兩個檔一格城堡都沒有 —— 所以規則放進去了,實際還觸發不到。
要真的走得到,得先還原 `sub_295AC` / `sub_297F4` 那條「野外開打時用周遭
地形組戰場」的路。那是另一件事,不併進這一份。

## 7. 這一份的教訓

- **「只有一處寫它」要看清楚寫的是什麼。** 字面量的寫入只有一處,
  但 `mov 變數, al` 那種寫入還有三處,其中一處才是真正的用途。
  `CLAUDE.md §4.5` 早就寫了「讀很多、寫只有 1 處 → 去看取址那幾筆」——
  同一條紀律,這次的破口是「寫的是暫存器」。
- **符號名旁邊那個位址是有意義的。** `byte_3F854` 與 `byte_3F844` 差 16,
  而列距 16 這件事**我自己在 `miscmap.go` 寫過**,還特地標了 ⚠。
  第一版沒去減那一下,就多繞了兩天。
- **地形碼要切出來看。** 「0x3C..0x3F 在地圖裡幾乎不存在」是對的,
  但那是因為它們只在**世界地圖**上、只在兩座城堡門口 ——
  切圖看到城垛與拱門之後,整件事才說得通。
