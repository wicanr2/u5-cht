| | |

## 1. 鏈

結局那一幕(`sub_135FC`)在整個執行檔裡只有兩個呼叫點,兩個都守著同一個條件:

```
sub_42CC   (戰鬥)     … cmp byte_3E0B0, 4Dh ; jnz …  → call sub_135FC
sub_163B0  (戰鬥收尾) … cmp byte_3E0B0, 4Dh ; jnz …  → call sub_135FC
```

`sub_135FC` 讀 `MISCMAPS.DAT` 位移 0x210(王座廳那張石室)與 `ENDMSG.DAT`,
印 "… lives!" / "Yes" / "No" / "He says" / "I see…" —— 確定是結局。

`0x4D` 是 `'M'`。問題收斂成:**誰把 `byte_3E0B0` 設成 `'M'`?**

---

## 2. 先更正兩個讀錯的東西

這一份的第一版有兩處讀錯,而且兩處都導向「這個條件大概永遠不成立」的結論。
兩處都不是讀得不夠仔細,是**沒去查那個符號到底是什麼**。

### 2.1 `byte_3E0B0` 不是「結局旗標」,是撤離方向

第一版寫「全檔只有一處寫它」。那句話只對**字面量 `'M'`** 成立 ——
`mov byte_3E0B0, al`(寫一個算出來的值)另有三處:

| 位置 | 是什麼 |
|---|---|
| `sub_27D24` | **存檔載入**,逐欄位 fgetc 的其中一格 → 它是存檔欄位 |
| `sub_2F0EC` | `sub eax, eax` 之後寫入 → 清成 0 |
| **`sub_15E20`** | ★ 真正的用途 |

`sub_15E20` 是**戰鬥撤離**:

```
if ((byte_3E08C & 0xF8) == 0x20) { 印 "Stay with ship!"; return 0 }
if (單位旗標 & 0x80) {
    if (byte_3E0B0 == 0)  byte_3E0B0 = 方向          // 第一個逃的人決定出口
    else if (方向 != byte_3E0B0 && (byte_3E0B1 & 0x80))
        印 "All must use the same exit!"; return 0
}
… 印 "Leave" 或 "Escape",離開戰場
```

方向由 `sub_15F18` 的跳表給,值是 1..4(西 / 東 / 北 / 南)。
而 `sub_16058` 另外用 **5 / 6** 呼叫同一支(印 "Up" / "Down"),
`sub_4074` 就靠這兩個值決定 `byte_3E0A5`(樓層)要加一還是減一。

⇒ **`byte_3E0B0` 是「這一場是怎麼離場的」:**

| 值 | 意思 |
|---|---|
| 1..4 | 從那一邊撤出戰場 |
| 5 / 6 | 往上 / 往下一層 |
| **0x4D 'M'** | **被吸收 → 播結局** |

`'M'` 是塞進同一格的**哨兵值** —— 一個不可能是離場方式的數字。
它也是**存檔欄位**(`sub_27D24` 逐欄位讀進來的其中一格),
所以理論上存檔裡塞 0x4D 就會在下一場戰鬥收尾時觸發結局。

### 2.2 `byte_3F854` 不是腳下那一格,是**正北**那一格

第一版把 `byte_3F854[戰場X]` 讀成「單位站的地形」,查不到對應的地圖資料,
於是推論「這個條件永遠不成立」。

真相在 `miscmap.go` 早就寫過的一句話上:**`byte_3F844` 是 11×11、列距 16 的
戰場 / 石室暫存**。三處獨立佐證:

```
sub_C414   byte_3F8F4[i*32 + j] = byte_3F844[i*16 + j]      i,j ∈ 0..10
sub_135FC  同一段搬運迴圈,一字不差
sub_295AC  byte_3F844[y*16 + x] = 某個位元組                執行期寫入(§4 說明是什麼)
```

而 `0x3F854 − 0x3F844 = 0x10 = 16` = **一列**。所以

```
byte_3F854[X]  ==  byte_3F844[1*16 + X]  ==  戰場 (X, 1)
```

`sub_161E4` 要求單位的戰場 Y == 2,查的卻是第 1 列 ——
**它看的是單位正北那一格。**

---

## 3. 條件

```
sub_161E4:
    單位 = dword_3EF50[byte_3E0AE]        // 這一回合行動的那個
    if (旗標 == 0)        return          // 空槽
    if (旗標 & 0x20)      return          // 已死
    if (戰場 Y != 2)      return
    if ((戰場[X][1] & 0xFC) != 0x3C) return
    byte_3E0B0 = 'M'
    印 "<某某> is absorbed!"
```

呼叫點只有一個:`sub_A360`(戰鬥迴圈)在每個單位行動完之後。

`dword_3EF50` 的 +6 / +7 是戰場 X / Y —— 這一點由 `sub_15F18` 獨立確認:
它把 `+6` 加上東西向的增量、`+7` 加上南北向的增量。

---

## 4. `byte_3F844` 是疊圖層,不是地形

⚠⚠ **本節推翻本檔第二版。** 第二版讀到「查的是正北那一格」之後,
就把 `byte_3F844` 當成戰場地形,推論「在城堡門口開打,城牆會進到戰場裡」。
**那是錯的**,而錯法與第一版同一型:**沒有把那個緩衝區的寫入者列完**。

全檔寫 `byte_3F844` 的只有五支,一支不多:

| 函式 | 寫什麼 |
|---|---|
| `sub_29D64` / `sub_C778` | `rep stosd` 整塊填 **0xFF**(0x2C dword = 176 B) |
| `sub_C414` / `sub_1DA10` / `sub_135FC` | `sub_2C740("MISCMAPS.DAT", byte_3F844, 0xB0, 位移)` —— 石室整份載入 |
| `sub_295AC` / `sub_297F4` | 逐格畫上**物件與 NPC 的 tile 位元組** |

`sub_297F4` 掃物件表 31→0,把每個物件換算成以玩家為中心的 11×11 視窗座標
(`byte_3E0A6 − 5`、`byte_3E0A7 − 5`),再 `byte_3F844[y*16 + x] = 物件.tile`。

⇒ **`byte_3F844` 是「這一格上面疊著什麼」那一層。**
地形從來不進去 —— 世界地圖與戰場的地形走的是另一條路(`byte_3F8F4`)。

所以條件的正確說法是:

> 活著的單位站在第 2 列,而**正北那一格的疊圖位元組**落在 0x3C..0x3F。

(空格是 0xFF,而 `0xFF & 0xFC = 0xFC ≠ 0x3C` —— 初值剛好不會誤觸。)

## 5. 而這在出貨的資料裡打不到

疊圖層只有三種來源,逐一掃過:

| 來源 | 0x3C..0x3F |
|---|---|
| 四張石室(`MISCMAPS.DAT` 0x000 / 0x0B0 / 0x160 / 0x210) | **0**(檔案裡唯一一次在 0x5A1,四張石室在 0x2C0 之前就結束了) |
| 物件表(`BRIT.OOL` / `UNDER.OOL` / `SAVED.OOL` / `INIT.OOL`) | **0** |
| NPC 的生物編號(`sub_1E74` 把它當 tile 寫進物件槽) | **0**(四份 `.NPC` 全掃,最小的非零碼是 1,再來就跳到 0x10 以上) |

⇒ **`sub_161E4` 在這個版本是死碼。** 第一版的直覺(「這個條件大概永遠不成立」)
是對的,只是當時的理由是錯的 —— 它以為 `byte_3F854` 是地形查表、
以為 0x3C..0x3F 不存在。真正的理由是「疊圖層裡放不進那個值」。

那 0x3C..0x3F 是什麼?**城堡的外牆與城門**(切圖看是白色城垛與黃色拱門),
而且在世界地圖上只有七格,全部圍著兩座城堡的入口:

| 座標 | 地形 | 誰 |
|---|---|---|
| (87,106) (85,107) (86,107) (87,107) | 3C 3D 3E 3F | 不列顛王的城堡(地點 17) |
| (197,244) (195,245) (197,245) | 3C 3D 3F | 黑棘的宮殿(地點 18) |

(用 `DATA.OVL` 0x3886 的 chunk 索引表把 `BRIT.DAT` 組成 256×256 再掃的;
`BRIT.DAT` 只存 205 個非全水 chunk,拿檔案位移硬換會算錯。)

它們是**地形**,而地形進不了疊圖層 —— 這正是這一條打不到的原因。
看起來像是原版留下的一段未完成路徑:程式碼寫了「站在城門下會被城堡吸進去」,
但沒有任何一條路把城門送進那個緩衝區。

## 6. 實作到哪裡

`checkAbsorbed()` 照 §3 + §4 寫好了,掛在每個單位行動完之後(同原版的呼叫點),
查的是疊圖層:石室看石室地圖,戰鬥看站在那一格的單位,其餘回 0xFF。
三條測試釘住:觸發、**只看正北的疊圖(地形不算、腳下不算)**、四個碼的邊界。

**這是死碼,而且刻意保留。** 「機制與原版一模一樣」包含把原版走不到的路
也照樣擺著 —— 自己補一條「讓它走得到」的路才是與原版不同。

### 那玩家到底怎麼走到結局?

在 **FM Towns 這一版,走不到**。`sub_135FC` 全檔只有兩個參照,都是直接呼叫,
**沒有任何取址**(整份 `.asm` 掃過)—— 也就是沒有跳表、沒有函式指標。
兩個呼叫點都守著死掉的 `'M'`。

光碟上也沒有第二個執行檔可以藏endgame:`.EXP` 只有 `U5OPEN.EXP`(開場)、
`TMENU/LABEL/DISKCOPY/FORMAT`(Towns 系統工具)與 `WORRIORS/WORRIORJ`。

⇒ **下一步是 DOS 版的 `ENDGAME.OVL`(2,800 B)。** 它是純機器碼、
一個字串都沒有(全檔只有一個 4 字元的可讀片段),所以要用 IDA 當
16-bit binary 載入並定基址才讀得動 —— 那是另一件事,不在這一份。
在那之前,真結局的入口只有王座廳那一幕本身(`docs/re/30`)。

## 7. 這一份的教訓

同一個錯誤犯了兩次,而且第二次是在「已經知道要小心」之後:

- **第一版**:說「全檔只有一處寫 `byte_3E0B0`」—— 只看了字面量的寫入,
  漏掉三處 `mov 變數, al`。真正的用途(撤離方向)在漏掉的那三處裡。
- **第二版**:說「`byte_3F844` 是戰場地形」—— 只看了**讀取**它的地方,
  沒把**寫入**它的五支列完。列完就會看到它整塊被填 0xFF、只收石室與物件。

兩次都是同一條紀律的破口:**要斷言一塊記憶體「是什麼」,先把寫它的人列完。**
`CLAUDE.md §4.5` 寫的是「讀很多、寫只有一處 → 去看取址那幾筆」;
這兩次的教訓可以合成一句更短的:**先數寫入者,再談語意。**

還有一條:
- **把任意位元組當 tile 畫,永遠會畫出一張看起來合理的圖。**
  查這條時我把 `MISCMAPS.DAT` 尾端 1,167 個未解位元組當成六張未知地圖渲染,
  出來是有水有樹的野外場景,像模像樣;逐列讀 hex 才看出整列 `00` 填充、
  數值全落在 0x00–0x1E。**渲染不是驗證。**
