# NPC 每回合的移動

> 輸入檔:`WORRIORS.EXP`(FM Towns,SHA-256 見 `re_work/fmtowns/SHA256SUMS.txt`)
> 日期:2026-08-07
> **狀態:已實作**(`internal/game/npcmove.go`)。同層移動逐格照原版;
> 跨樓層的樓梯口選擇還沒還原,見 §5。

`.NPC` 檔只回答「幾點該在哪」。「這一回合 NPC 做什麼」由另外三層決定:

```
sub_8924(hour)   進場景時建立執行期狀態
   ↓
sub_9690(hour)   每回合跑一次,對 32 個 NPC 各做一次
   ├ sub_91A4    判行為模式(要走?要上下樓?還是玩家看不到直接搬)
   ├ sub_8BA0    尋路 —— 內含 sub_8A1C 建格子圖 + 環狀佇列 BFS
   └ sub_9428    「這一格站得上去嗎」
```

---

## 1. 執行期狀態(`word_3E770`,32 × 16 B)

由 `sub_8924` 的初始化逐行讀出來:

| 位移 | 內容 |
|---|---|
| +0 | 行為模式(0 = 這個槽沒人) |
| +2 | X |
| +4 | Y |
| +6 | 樓層 |
| +8 | 生物編號(取自 `byte_3EDB0[npc]`) |
| +A | 沒有寫入處 |
| +C | 這個 NPC 佔用的**物件槽號** |
| +E | 目前採用的排程 slot |

+C 這一欄很關鍵:**NPC 在場景裡是透過物件槽畫出來的**。這印證了
`docs/re/11 §3` 的「進場景時清空物件表,再由場景系統重新填」。

另外兩張平行表:

- `word_3ED70[npc]` —— 路徑索引;`0xFFFF` = 目前沒有路徑
- `byte_3E970[npc*32]` —— 路徑本身,**(步數, 方向) 成對**,共 16 段
- `word_3EDD4[npc]` —— 尋路連續失敗次數

---

## 2. 行為模式(`sub_91A4`)

只有在排程的四個時刻**之一正好是現在**時才重新評估;其餘時候沿用舊模式。
這就是 NPC 在整點換班、而不是每回合重新決定要去哪的原因。

判定只看三個樓層的關係 —— NPC 現在在哪層(`from`)、目標在哪層(`to`)、
玩家在哪層(`here`):

| 條件 | 模式 | 意思 |
|---|---|---|
| 新 slot == 舊 slot | 1 | 已經在崗位上,不動 |
| `here != from` 且 `here != to` | 8 | 玩家看不到 → **直接搬過去** |
| `here == from == to` | 2 | 同層,走過去 |
| `here == from`,`to > here` | 6 | 在玩家這層,要上樓離開 |
| `here == from`,`to < here` | 7 | 在玩家這層,要下樓離開 |
| `here == to`,`from > here` | 4 | 在別層,要下來找玩家這層 |
| `here == to`,`from < here` | 5 | 在別層,要上來 |

尾端還補一條:若 X / Y / 樓層都已經等於目標,直接算模式 1。

⇒ **模式 8 的行為就是瞬移**,而且它涵蓋了「玩家不在那一層」的所有情況。

⚠ 還有一條容易漏的:`sub_9690` 用 `cmp word ptr [ebx], 1 / jg` 判斷 ——
**只有模式 ≤ 1(不存在或閒置)才重新呼叫 `sub_91A4`**。正在移動中的 NPC
直接繼續走。漏了它的話,因為「換班時刻」整整持續一小時,NPC 會每分鐘被打回閒置,
路徑算得出來卻一步都走不了。我第一版就是這樣。

## 3. 尋路

### 3.1 建格子圖(`sub_8A1C`)

在一塊 32×32 的 buffer(`dword_3EF4C` 指向)裡標出每一格的狀態:

```
for y, x in 0..31:
    grid[y*32+x] = sub_9358(x, y, floor, npc, slot) ? 0 : 0x90
    if 模式 < 0 且 byte_400F4[y*32+x] == 0xC8/0xC9(樓梯) → grid = 5
; 別的 NPC 與隊伍站的格子:離目標 4 格以上才擋(近了就讓路)
for slot 31..1: if 物件種類 > 0x3F 且 距目標 >= 4 → grid[該格] = 0x90
同樣處理槽 0(隊伍自己)
if 模式 > -1: grid[目標] = 5
grid[起點] = 0x46
```

編碼:`0` 未訪問、`0x90` 阻擋、`5` 目標、`0x46` 起點,
搜尋過程中高 4 bit 會被填成「從哪個方向來」。

「離目標 4 格以內的 NPC 不算障礙」這條有點反直覺,但它讓 NPC 能擠到目的地
附近而不會互相卡死。

### 3.2 環狀佇列 BFS(`sub_8BA0`)

```
queue 是 32 格環狀(x[] 與 y[] 兩條),head = 0, tail = 1, queue[0] = 起點
while head != tail 且 未找到:
    (x, y) = queue[head]
    dir = grid[y*32+x] >> 4          ; 起點是 0x46 >> 4 = 4
    重複 4 次:
        依 dir 取鄰格   1=西(x−1)  2=南(y+1)  3=東(x+1)  4=北(y−1)
        沒越界(0..31)時:
            v = grid[鄰格]
            if v < 0x10:                     ; 還沒訪問過
                grid[鄰格] = dir << 4        ; 記下從哪來(低 4 bit 被清掉)
                if v == 5: 找到了,回報座標,結束
                else if tail != head: queue[tail++] = 鄰格
                if tail >= 32: tail = 0
        dir = (dir & 3) + 1                  ; 1→2→3→4→1
    head++; if head >= 32: head = 0
```

兩個容易漏掉的地方:

1. **方向的嘗試順序取決於「這一格是從哪個方向來的」** —— 從那個方向開始
   依 1→2→3→4 循環,不是固定的上下左右。所以路徑的長相與「怎麼走到這格」有關。
2. **佇列只有 32 格,滿了就不再加入**(`if tail != head` 那個判斷)。
   這不是完整的 BFS,是**有界搜尋**;搜不到就是搜不到。

### 3.3 重試節流

`sub_9690` 不是每回合都重算路徑:

```
if word_3EDD4[npc] >= 200 → 放棄
if word_3EDD4[npc] != 0 且 random(0,2) != 1 → 這回合不重算
```

也就是第一次失敗後,之後每回合只有約 1/3 的機率重試,連續失敗 200 次才死心。

### 3.4 走一步(`sub_9428`)

```
座標必須在 0..31
tile & 0xFC == 0x30           → 可以(門)
NPC 種類是 0xFC               → 可以
tile & 0xFC == 0x90 且 模式 != 2 → 不行
其餘 → 交給下一層(通行判定 + 有沒有人佔著)
```

走成功之後:更新物件槽的 +2/+3 與執行期狀態的 +2/+4、路徑的步數 −1、
失敗計數歸零;步數歸零就把路徑索引 += 2 取下一段。

### 3.5 通行判定(`sub_9358`)有兩層,而且寬鬆度不同

```
目標格             → 一律通過(函式一開頭就回 2,不看地形)
座標越界           → 用 byte_404F3 當 tile(那是地圖最後一格,原版的 quirk)
tile 0xC8 / 0xC9   → 只有模式 3(正在找樓梯)的 NPC 能踩
其餘               → 查 byte_54524 的 bitmap
```

⚠⚠ **`byte_54524` 不是玩家那張通行表。** 玩家走 `byte_5FF6C`,NPC 走這張,
兩者有 **89 個 tile 判定不同** —— 最明顯的是 tile 16..25(馬與各種載具):
玩家站得上去,NPC 不行。拿玩家那張給 NPC 用,NPC 就會走到船上與馬背上。

另外,**建格子圖與實際走一步用的是兩套寬鬆度**:

| | 建圖(`sub_8A1C`) | 走一步(`sub_9428`) |
|---|---|---|
| 地形 | `sub_9358` | `sub_9358` |
| 別的 NPC | 離目標 **≥ 4 格**才算障礙 | `sub_2B3DC`:有人就是不能走 |

建圖寬鬆是為了讓 NPC 能規劃到目的地附近而不被同事卡死;真的走過去時嚴格,
走不過去就整條路徑作廢、下回合重算。

### 3.6 ⚠⚠ 兩張方向表互為相反

這是整段最容易踩的地雷,我第一版就踩了:

| dir | BFS(`sub_8BA0`) | 走路 / 回溯(`sub_8EA4`、`sub_8D28`) |
|---|---|---|
| 1 | x − 1(西) | x + 1(東) |
| 2 | y + 1(南) | y − 1(北) |
| 3 | x + 1(東) | x − 1(西) |
| 4 | y − 1(北) | y + 1(南) |

兩張表混用的話,BFS 與回溯**各自都正確**,但走出來的路徑會往反方向跑 ——
症狀是 NPC 沿著一條看起來合法的路徑穿牆而過,最後走出地圖邊界。

也因為兩表相反,`sub_8D28` 尾端反轉序列時才要把方向也反向
(`((d+1)&3)+1`):回溯是用走路那張表在「倒著走」,反轉之後方向自然要翻過來。

## 4. 驗收

`internal/game/npcmove_test.go`:

- 兩張方向表互為相反(`bfsStep` 走一步、同 dir 的 `walkStep` 走回原地)
- NPC 通行表與玩家的差 89 個 tile,且 tile 16..25 擋 NPC
- 換班後 NPC 是**一步一步**走的(每回合位移的曼哈頓距離 ≤ 1,不會一口氣跳)
- 一整天每 7 分鐘取樣:NPC 站的格子要嘛 NPC 走得上去,要嘛是它三個崗位之一
  (床、椅子這類 tile 擋一般通行,但崗位就在上面 —— 目標格一律放行)
- 一整天每 11 分鐘取樣:沒有兩個 NPC 站在同一格

## 5. 還沒還原的

- **跨樓層的樓梯口選擇**(模式 4/5/6/7):原版先用 `sub_89EC` 找樓梯、走過去、
  再換層。目前直接換層 —— 這是本檔唯一還沒逐格對上原版的地方,
  而它只在 NPC 換樓層的那一刻發生。
- **`sub_94E0`** —— 尋路失敗時的 fallback(疑似隨機遊走),還沒讀。
- 原版的重試節流用 `random(0, 2) == 1`;這裡用時鐘當種子讓 headless 可重現,
  與問候語挑句同樣的理由。
