# 64 — Hercules:16×12 的字型,與四筆位元圖樣

| | |
|---|---|
| 輸入檔 | `HER.DRV`(9,087 B)、`IBM.HCS` / `RUNES.HCS`(各 3,072 B)、`TILES.4` |
| 落地 | `internal/u5data/font.go`(`HCSCharset`)、`internal/u5data/tiles.go`(`HerculesPattern`) |
| | `u5dump tiles-her`、`u5cht -display Hercules` |
| 前一篇 | `docs/re/62`(四種顯示模式)把這一條列為「還沒做」 |

`docs/re/62` 說 Hercules「沒有自己的 tileset,單色轉換規則要逆 `HER.DRV` 才知道」。
逆了。而且順帶解掉一個沒人問過的問題:那兩個 `.HCS` 是什麼。

## 一、`IBM.HCS` / `RUNES.HCS` 是 16×12 的字型

各 3,072 B = 128 glyph × 24 B。24 B 有兩種切法都整除,**但只有一種看得出字**:

```
8 × 24  的 glyph 65        16 × 12 的 glyph 65
........                   ................
.....###                   .....########...
#####...                   ....###...###...
....###.                   ...###....###...
..###...                   ...##########...
...###..                   ...###....###...
..###...                   ...###....###...
...#####                   ..###.....###...
#####...                   .###......####..
...(一團斜線)               ................
```

**16×12。** 整張表(0x20..0x7F)畫出來是完整的 ASCII:空白、標點、數字、
大小寫字母,最後幾格是畫框用的圖形字元 —— 與 `IBM.CH`(8×8)同樣**索引 = ASCII 碼**。

幾何上也說得通:Hercules 是 720×348,720 / 16 = 45 欄、348 / 12 = 29 列。
相對於 DOS 的 8×8 @ 320×200,是**橫向 2 倍、縱向 1.5 倍**。

⚠ `RUNES.HCS` 有 14 格是空的:`! # $ % & ( ) < = > ?` 與 **`x y z`** ——
不列顛符文表沒有那幾個。那是資料本身,不是解析錯誤,測試要放行。

## 二、`HER.DRV` 裡的三張表

`HER.DRV` **沒有任何 `int 10h`** —— Hercules 不在 BIOS 支援範圍內。
需要的東西全部在檔案裡,而且都不是猜的:

| 位移 | 長度 | 內容 | 是什麼 |
|---|---:|---|---|
| 0x070C | 12 B | `35 2D 2E 07 5B 02 57 57 02 03 00 00` | **標準 Hercules 圖形模式的 6845 參數表**,一個位元組都不差 |
| 0x071A | | `mov al,1 / mov dx,3BFh / out dx,al` | 設定暫存器:允許圖形模式 |
| 0x0734 | | `mov dx,3B8h / out dx,al` | 模式暫存器 |
| **0x0318** | **4 B** | **`00 55 AA FF`** | ★ 色號 → 位元圖樣 |
| 0x031C | 16 B | `00 03 0C 0F 30 33 3C 3F C0 C3 CC CF F0 F3 FC FF` | 每個 bit 複製成兩個 = **橫向 2 倍** |
| 0x032C | 8 B | `80 40 20 10 08 04 02 01` | 單一位元遮罩 |

0x031C 那張表值得看一眼:`0001`→`00000011`、`0010`→`00001100`、`1111`→`11111111`
—— 就是「四個像素變八個」。與字型 16 寬(而 DOS 是 8)是同一件事的兩個出口。

### ★ 用到圖樣表的地方

兩處,而**兩處都是在講顏色**:

```asm
; #15 @0x09E4  設定畫筆顏色
        and     ax, 3
        mov     bx, 0318h
        xlat
        mov     cs:[0334], al    ; ← 目前的抖動位元組

; #31 @0x1282  畫字(前景 / 背景各一個色號)
        and     dx, 0303h        ; ★ DL 與 DH 各取**低 2 bit**
        mov     bx, 0318h
        mov     al, dl / xlat / mov cs:[130E], al   ; 前景圖樣
        mov     al, dh / xlat / mov cs:[130F], al   ; 背景圖樣
        …
        mov     ax, 0B000h       ; ← Hercules 的顯示記憶體區段
```

兩處都把色號夾成 **2 bit** → Hercules 的顏色空間就是 2bpp 那四色,與 `TILES.4`
的色數一致。「Hercules 沒有自己的 tileset,那它畫什麼」到此結案:**它畫 CGA 那一份**。

⚠ **更正(見文末追記)**:本節原本寫「`and dx,0303h` 是關鍵,所以 Hercules 吃 `.4`」
—— 那條推論**引錯了常式**。`and dx,0303h` 是字的前景 / 背景色,與圖磚資料無關;
驅動程式唯一的圖形 blit 收的是 **1bpp**。結論(色數是 4)沒變,支持它的證據換了。

### 四個圖樣的語意

```
色號 0 → 0x00  全暗
色號 1 → 0x55  隔一點亮(50%,相位 A)
色號 2 → 0xAA  隔一點亮(50%,相位 B)
色號 3 → 0xFF  全亮
```

中間兩色都是 50% 灰但**相位相反** —— 所以色號 1 與 2 的區域相鄰時分得出來。
而且**四筆就是全部**:若原版還要依列號交替相位,表就得有八筆。

## 三、落地與誠實的界線

`LoadTileSetFor(dir, DisplayHercules)` 讀 `TILES.4`,每個像素取
「圖樣在該 x 位置的那個 bit」,亮的給色號 15、暗的給 0 —— 算繪層因此不必為單色
另開一條路。畫出來的圖山脈、樹、城堡、桌椅、船、墓碑、十字架都認得出來。

⚠ **還沒追完的**:16×16 的 tile 到 Hercules 畫面上那一格的**完整 blit 迴圈**
(位元加倍表怎麼與圖樣表配合、縱向 1.5 倍怎麼放)。所以現在產出的是 **1× 的
16×16 單色圖**,那正是圖樣表自己說的規則,不多加任何未經證實的縮放假設。

⇒ 這**不是逐像素重現原版的 Hercules 畫面**。`u5cht -display Hercules` 會在啟動時
印一句話說明(`CLAUDE.md` §3.0:缺的部分要明說,不要讓玩家以為是完整的)。

## 追記:blit 迴圈追完了 —— 640×300 置中在 720×348

上面那句「還沒追完」是本篇唯一的缺口。追完之後答案比預期乾淨,而且
**原本的問法本身有個錯誤假設**:加倍表與圖樣表**從來不會一起用**。

落地在 `internal/u5data/hercules.go`(常數 + `BuildHerculesScanlineTable`),
八條測試對著 `HER.DRV` 的位元組跑。

### 一、驅動程式有一張 38 筆的進入點表

`HER.DRV` 開頭是 38 個 `jmp near`,每筆 3 B,共 **0x72 B**:

| # | 位址 | 是什麼 |
|---:|---|---|
| 15 | 0x09E4 | 設定畫筆顏色(色號 0..3 → 圖樣位元組,存 0x0334) |
| 16 | 0x09F4 | **畫點**(內層 0x0A3C) |
| 26 | 0x118C | **畫 1bpp 圖形**(shape blit) |
| 31 | 0x1282 | **畫字**(`.HCS` 的 16×12 字模) |
| 34 | 0x1C83 | 畫面溶解特效(LFSR 逐點消去 + 關 PC 喇叭) |
| — | 0x06F6 | 「沒實作」的 `retf` 樁,**8 筆**指到它 |

有進入點表這件事本身就是禮物:不必猜哪一段是什麼,**呼叫編號就是語意**。

### 二、掃描線位址表在 0x0072,300 筆

表**不在檔案裡**(0x0072 起 600 B 在磁碟上全是 0),由 0x0770 建:

```asm
        mov     si, 0072h        ; ★ 剛好接在 38 筆進入點表(0x72 B)之後
        mov     cx, 012Ch        ; ★ 300 條掃描線
        mov     bx, 005Ah        ; 每列 90 位元組 = 720 像素
        mov     ax, 0221h        ; 第一條的位移 = 6×90 + 5
        mov     dx, 2000h        ; Hercules 的 bank 大小
@@:     mov     [si], ax
        add     si, 2
        add     ax, dx           ; 下一個 bank
        jns     @F               ; 還沒溢出 bit15 → 直接寫下一筆
        and     ax, 7FFFh        ; 溢出 → 回 bank 0
        add     ax, bx           ;         並前進一列
@F:     loop    @B
```

Hercules 經典的**四路交錯**:位址 = bank×0x2000 + 列×90 + 欄。
沒有除法、沒有取餘數,只有加法與一次遮罩 —— `jns` 兼作「加了四次沒有」的計數器。

**三個獨立數字把表的長度釘死**:

1. 迴圈計數 `cx = 300`。
2. `0x0072 + 300×2 = 0x02CA`,而 0x02CA 正是**下一個變數**(離屏緩衝的段值,
   全檔有 `mov es, cs:[02CA]`)。多一筆或少一筆都會撞到它。
3. 起始位移 0x0221 = 545 = **6×90 + 5**;照交錯公式回推,第 i 筆對應的
   實體掃描線正好是 **24 + i**,而位元組欄一律是 **5**。

### 三、幾何全部收斂

畫點那支(0x09FD)一開頭就把座標夾住:

```asm
        cmp     ax, 0     / jl  reject
        cmp     ax, 013Fh / jg  reject      ; ★ 319
        cmp     bx, 0     / jl  reject
        cmp     bx, 00C7h / jg  reject      ; ★ 199
```

**呼叫端用的是原版的 320×200 座標**,放大是驅動程式自己的事:

```
X:  位元組 = x >> 2       相位 = x & 3      ← 一個來源像素佔 2 bit = 橫向 2 倍
Y:  bx = (y × 3) & FFFEh  →  表項 bx/2,而且**同一列畫兩條**(bx 與 bx+2)
```

縱向那條算式攤開來就是「1.5 倍」的全部:

| 邏輯列 | 掃描線表項 |
|---:|---|
| 0 | 0, **1** |
| 1 | **1**, 2 |
| 2 | 3, **4** |
| 3 | **4**, 5 |
| 4 | 6, **7** |
| 5 | **7**, 8 |

**每兩列來源 = 三條掃描線**,交界那條由兩列以 `or` 疊上去。
**四支不同的常式算的都是這一條式子**:畫點 0x0A3C、圖形 0x11DD、
溶解 0x1D0D、以及清單列 —— 這種「四處獨立同構」比任何單點證據都硬。

橫向那邊:清一列文字是 `mov cx,28h; xor ax,ax; rep stosw`,捲動 / 淡化
(`and ax,5555h`)也是 `cx = 28h` → **40 字 = 80 位元組 = 640 像素**。

⇒ **實際畫面 640×300,置中在 Hercules 的 720×348**:
`(348−300)/2 = 24`、`(720−640)/2 = 40`,與表的起始值 24 + i、欄 = 5 逐一對上。

而 640×300 對 320×200 正好是**橫 2 倍、縱 1.5 倍** —— 與 `.HCS` 字型
8×8 → 16×12 是同一個比例(這是 16×12 的**第三份**獨立佐證)。字格數因此完全不變:

| | 解析度 | 字模 | 字格 |
|---|---|---|---|
| DOS | 320×200 | 8×8 | **40 × 25** |
| Hercules | 640×300 | 16×12 | **40 × 25** |

驅動程式對遊戲呈現的是一個**與其他三種模式一模一樣的 320×200 / 40×25 世界**。
這解釋了為什麼遊戲主體完全不必知道 Hercules 存在,也是為什麼引擎在
320×200 邏輯座標上畫圖是對的抽象層。

### 四、加倍表與圖樣表:不在同一個軸上

這是原本那句「還沒追」真正的答案 —— **兩張表從來不會一起用**:

| 表 | 筆數 | 管什麼 |
|---|---:|---|
| 0x031C | 16 | **幾何**:1bpp 的一個 nibble(4 個來源像素)→ 一個位元組(8 個螢幕像素) |
| 0x0318 | 4 | **顏色**:色號 0..3 → 抖動位元組(00/55/AA/FF) |

兩支 blit 各只用一張:

**#26 圖形 blit(0x118C)** —— 來源是 **1bpp**:

```asm
        lodsb                            ; 一個位元組 = 8 個來源像素
        ; 拆成兩個 nibble(cl = 4 → 高、cl = 0 → 低,cl 減到 −4 才讀下一個位元組)
        and     bx, 0Fh
        mov     bl, cs:[031C+bx]         ; ★ 加倍:4 個來源像素 → 8 個螢幕像素
        ; 對齊的情況
        or      es:[di], bl              ; 第一條掃描線
        or      es:[<第二條>], bl        ; 第二條掃描線 ← 縱向 1.5 倍就在這
        ; 沒對齊(相位 ≠ 0)
        mov     cl, dl / shl cl, 1       ; 相位 × 2(因為橫向已加倍)
        mov     ch, 0FFh / shr ch, cl    ; 本位元組的遮罩
        ror     bl, cl                   ; ★ 用 ror,掉出右邊的 bit 從左邊回來
        mov     bh, bl
        and     bl, ch / not ch / and bh, ch
        or      es:[di], bl / or es:[di+1], bh
```

圖形目錄:`ds:[0]` = 筆數、`ds:[2+idx×2]` → `{u16 寬(像素), u16 列數, 位元…}`;
寬度計數每個 nibble 減 4 —— 兩個獨立線索都說來源是 1bpp。

**#31 字 blit(0x1282)** —— `.HCS` 的字模**已經是 16×12**,不需要放大:

```asm
        shl     ax, 1                    ; 欄 × 2 = 位元組欄(一個字 16 像素 = 2 B)
        ; bx = 列 × 12 ← ★ 直接就是絕對掃描線編號
        mov     cx, 000Ch                ; 12 條掃描線
@@:     mov     di, cs:[<列 × 2>+0072]
        add     di, bx
        mov     al, cs:[130F] / mov ah, al / mov es:[di], ax   ; 先用背景圖樣填 16 像素
        lodsw                            ; ★ 字模一列 16 bit(2 B/列)
        jz      @F                       ; 空列跳過
        mov     bx, ax / not bx / and es:[di], bx / not bx     ; 挖洞
        and     bl, cs:[130E] / and bh, cs:[130E]              ; 前景圖樣 & 遮罩
        or      es:[di], bx
@F:     inc     dx / loop @B
```

一列只寫**一條**掃描線(`cx = 0Ch`、`lodsw`)—— 因為 12 = 8 的 1.5 倍
**已經烘在檔案裡**。

⇒ **字型是「預先放大」,圖形是「blit 時放大」。同一個 1.5 倍,兩條路。**
這也回答了 `.HCS` 為什麼要單獨存一份 16×12:8×8 拉到 16×12 沒法只靠加倍表
(縱向 1.5 倍會讓字的橫筆畫在共用掃描線上黏成一團,字型必須手工重畫)。

### 五、順帶解掉的兩個小東西

- **0x0308 / 0x030C**(各 4 B):`3F CF F3 FC` 與 `C0 30 0C 03` —— 相位 0..3 的
  2 bit 遮罩與其補數,高位在左。畫點是「`and` 保留遮罩把該像素挖掉,再 `or` 圖樣」。
  `cs:0x02CC` 非 0 時改走 `xor es:[bx], ah` —— 那是反白 / 擦除筆。
- **0x0336..0x0435**(256 B):檔案裡是**整個位元組反轉表**(`00 80 40 C0 20 …`),
  被 0x0C66 那支(用它 + 加倍表)拿去畫**左右鏡像**的圖形。
  ⚠ 而 0x078F 的初始化迴圈會把它**改寫**成
  `((v&0C)<<4) | (v&30) | ((v&C0)>>4)`(= 2 bit 一組反轉再左移 2)——
  兩者不同,誰在什麼時機用哪一份尚未追,先記在這裡不下結論。

### 六、還沒解決的一段(誠實記帳)

驅動程式**只收 1bpp** 圖形,所以「16×16 的 2bpp tile 怎麼變成單色」這件事
**不在驅動裡**,在遊戲本體某個 `.OVL`。`HerculesTile` 用的規則(取圖樣在該 x
位置的那個 bit)是驅動自己的圖樣表所指的規則,但**轉換發生在哪、是否逐列換相位**
尚未證實。

另外 `hercules.go` 只重現**幾何**;`internal/render` 仍在 320×200 邏輯座標上畫圖,
沒有真的產生 640×300 的 Hercules 位元圖。要逐像素重現得再走一步。
