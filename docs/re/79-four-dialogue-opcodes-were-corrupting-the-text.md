## 1. `sub_1C1E8` 是一個「吃參數的 opcode」分派器

```asm
switch (byte_55F18) {
  0x85: 收 3 個位元組 → sub_1B854()          ; 索取金幣
  0x86: sub_1B964(這個位元組 & 7Fh)          ; 給玩家一樣東西
  0x8C: sub_1C1C8(NPC 索引) → 條件跳轉
  0xFE: 收 2 個位元組 → 業報門檻跳轉
}
```

引擎的 opcode 表有 0x81/82/83/84/87/88/89/8A/8B/8D/8E/8F/91–9F/FF ——
**這四個一個都沒有**。

## 2. ★★ 真正的症狀:它們的參數被當成文字展開

引擎的展開器是 `for _, ch := range raw` —— **沒辦法跳過參數位元組**。所以:

| 位元組 | 原本被當成 |
|---|---|
| `0x85` 本身 | `ch >= DictLiteralMin`(0x81)→ 印成控制字元 `0x05` |
| 三個 ASCII 數字(0x30..0x39) | **小於 0x81 → 當成詞典索引查表** |

⇒ 一句「索取 100 金幣」會展開成一個控制字元加**三個不相干的常用詞**。

★ 這是一個**看得見但看不懂**的 bug:玩家看到的是語意不通的句子,
而不是崩潰或空白。而修法不是「跳過它們」—— 是把整個展開器改成索引迴圈,
因為 opcode 與參數是**一個語法**,不是兩件事。
`TestArgumentBytesDoNotLeakIntoTheText` 對四個 opcode 逐一要求 `text == ""`。

## 3. opcode 0x85 —— 金額寫在對話文字裡

```asm
byte_55F1A[++byte_55F19] = 這個位元組
if (byte_55F19 == 3) call sub_1B854
```

`sub_1B854` 把三個位元組當十進位數字:

```asm
(byte_55F1B & 7Fh) × 100 − 12C0h        ; 12C0h = '0' × 100
(byte_55F1C & 7Fh) × 10  − 1E0h         ; 1E0h  = '0' × 10
(byte_55F1D & 7Fh)       − 30h
```

`if (價格 > 金幣)` → `"Thou hast not enough gold!"` 並繼續對話
(`sub_1BF08` 回到「Your interest?」);否則扣錢。

⚠ 比較是 **`jg`(大於)才拒絕** ⇒ **剛好夠付得出來**。

### ★ 扣完錢之後那一段業報獎勵**先不做**

```asm
kind = 物件[這個 NPC].kind & 0FCh
if (kind == 6Ch && byte_3E09B >= 100) {
    byte_3E09B = 0
    業報 +1(上限 99)
    if (金幣 == 0) 業報 +2          ; ★ 把錢全部給光,再加 2
}
```

`byte_3E09B >= 100` 是一個**節流條件**,而那個變數的語意還沒定
(WORKLIST 上仍是 ⬜)。做了會變成「每次給錢都加業報」——
**缺一段比多一段錯的好**(`CLAUDE.md` §3.0)。

## 4. opcode 0x86 —— `sub_1B964` 的十一種資源加一族裝備

```
參數 < 0x40 → byte_3DFD0[參數] += 1(上限 99)      ★ 背包裝備那一格
'A' → 糧食 +1(上限 9999)    'G' → 魔毯 +1
'B' → 金幣 +1(上限 9999)    'H' → byte_3DFCA = 0FFh   六分儀
'C' → 鑰匙 +1                'I' → byte_3DFC8 = 0FFh   望遠鏡
'D' → 寶石 +1                'J' → byte_3DFCC = 0FFh   徽章
'E' → 火把 +1                'K' → 骷髏鑰匙 +1
'F' → 抓鉤 +1
```

⚠ 三個信物是**直接寫 0xFF**,不是 +1 —— 它們是有/沒有,不是數量。
兩種加法也是兩支函式:`sub_2BBB8(ptr, 1, 99)` 對位元組、
`sub_2BBDC(ptr, 1, 0x270F)` 對 u16(糧食與金幣,上限 9999)。

## 5. ✅ 順帶把三個「位移未釘死」的旗標結案

`docs/re/44` §4 記著「望遠鏡 / 六分儀 / 懷錶的持有旗標存檔位移還沒釘死,
所以 U 的清單**無條件列出**它們」。現在有兩條互不相干的證據:

1. `sub_1A5E8` 的跳表 **case 標註直接給名字**:`aSpyglass` = 32、
   `aPlans` = 33、`aSextant` = 34、`aWatchThePocket` = 35、`aBadge` = 36、
   `"Box"` = 37,而 `sub_1E8D4` 把 `byte_3DFC8`..`byte_3DFCD` 抄成 +32..+37。
2. `sub_1B964` 的三個信物寫的位址:`'H'` → `byte_3DFCA`、
   `'I'` → `byte_3DFC8`、`'J'` → `byte_3DFCC` —— 與上面逐一相符。

⇒ 存檔位移:望遠鏡 **0x0214**、圖紙 0x0215(已驗)、六分儀 **0x0216**、
懷錶 **0x0217**、徽章 **0x0218**、檀香木盒 0x0219(已驗)。
兩端被已驗過的欄位夾住,中間四筆沒有滑動空間。

三個旗標已進存檔(round-trip 有測試),而 U 的清單改成**照旗標列** ——
不再無條件列出三樣可能沒有的東西。

## 6. opcode 0x8C / 0xFE —— 條件算得出來,落點還沒接

```asm
sub_1C1C8(bit):  return (dword_3E3E8[地點] >> bit) & 1
```

`dword_3E3E8[地點]` 就是 `OpAskName`(0x88)寫進去的那個遮罩 ——
**每個地點一個 32 位元,位元 i = 這座城的第 i 個 NPC 認得汝了**
(引擎的 `State.Introduced` / `KnowsThyName`,`docs/re/06` 已有)。

⇒ **0x8C =「這個 NPC 已經認得汝的話,跳到第 N 則回答」**;
第二個參數 **0xFF 代表「不跳,直接繼續」**。

⇒ **0xFE =「業報 ≥ 門檻才跳到第 N 則」**;業報不足時什麼都不做。

⚠ **兩個條件都算得出來,但「跳到第 N 則回答」需要一個照編號取回應的入口**,
而引擎的 `RespondAt` 是照關鍵字找的。所以條件成立時先印一句誠實的說明
(`MsgTalkJumpNotWired`),不假裝跳了。⬜ 留在下面。

## 7. 還沒讀的

- ⬜ **照編號取回應的入口**(`byte_55F32` → `sub_1C0AC`)。0x8C 與 0xFE 都要它,
  而 0x91–0x9F 的提問區塊應該也是同一個機制 —— 值得一起做。
- ⬜ `byte_3E09B >= 100` 的語意(乞丐業報的節流條件)。WORKLIST 上原本記
  「進餐計數器」,而這裡的用法對不上那個猜測 —— **兩處用途不一致就是一條 finding**。
- ⬜ 物件種類 `& 0xFC == 0x6C` 是哪一種 NPC(乞丐?)。`(0x6C − 0x40)/4 = 11`
  → 生物名表第 11 筆,還沒去對。
- ⬜ 徽章(0x0218)還沒接進 `u5data.Save` 的欄位;位移已釘死,`HasBadge`
  目前仍只在記憶體裡。
- ⬜ `sub_1BF08`(`Your interest?` / `BYE`)—— 付不出錢之後回到的那一支,未讀。

## 追記(同日)—— 兩個條件跳轉的落點就是提問區塊,而 0x8C 只吃一個參數

§6 把「跳到第 N 則回答」列成 ⬜,理由是「引擎的 `RespondAt` 是照關鍵字找的」。
追 `byte_55F32` 的讀取點就發現那個 ⬜ 是誤判 —— **三支掃描函式都一樣**:

```asm
sub_1BCB8 / sub_1BD0C / sub_1C00C:
    dword_55F14 = byte_54700                 ; 對話緩衝開頭
    while (*dword_55F14 != byte_55F32)
        sub_1BA80(0x90, 0x9F)                ; 前進到下一個 0x90..0x9F 標記
```

⇒ **`byte_55F32` 是提問區塊的碼(0x90..0x9F)**,而那個掃描就是「往前找到
第一個開頭位元組等於它的區塊」。引擎的 `QuestionAt(code)` **正是同一個查法**,
`ask(code)` 已經在用它(0x91–0x9F 走的就是這條)。

⇒ 兩個條件跳轉直接借 `ask()` 就接完了。**缺的從來不是入口,是我沒去追
那個變數的讀取點就先寫了 ⬜。** 這與 `docs/re/77` 的木盒是同一個形狀:
**在斷言「還沒有 X」之前,要先去找 X**(`rulebook/62`)。

### ⚠ 而順手抓到自己的一個解析錯誤:0x8C 只吃一個參數

```asm
loc_1C272:                       ; case 0x8C
    byte_55F18 = 0; byte_55F19 = 0
    push dword_55E6C             ; ★ 參數是「當前 NPC 的槽號」,不是腳本位元組
    call sub_1C1C8
    jz → return 0                ; 這個 NPC 還不認得汝 → 什麼都不做
    cmp bl, 0FFh
    jz  → sub_1BF08()            ; ★ 0xFF = 不跳,回到「Your interest?」
    byte_55F32 = bl              ; 否則跳到那個提問區塊
```

`sub_1C1C8` 的參數是 **`dword_55E6C`(當前 NPC)**,所以腳本裡那一個位元組
是**目標**,不是「要測哪個位元」。我第一版讀成兩個參數 ⇒ **會多吃掉後面
文字的第一個字**。

`TestBothConditionalJumpsCarryTwoArguments` 現在多一條:
`{0x8C, 0x93, 'A'|0x80}` 展開後的文字必須**正好是 `"A"`** ——
多吃一個位元組這條就紅。

⇒ 教訓:**「這個 opcode 吃幾個參數」要從呼叫端的 `push` 讀,
不能從「它需要幾個資訊」推。** 我是照語意推的(要測哪個位元 + 跳去哪),
而原版把其中一個資訊放在別的地方。
