## 1. 起點:`Attacked from the north` 是地牢的事

`DATA.OVL` 0x2DA2 那幾句 `Attacked from the north/east/south/west`,
`WORKLIST` 一直掛在「戰鬥」底下標 ⬜。實際上組出這句的 `sub_5008`
只有一個呼叫者 —— `sub_5150+74`,而 `sub_5150` 是**地牢的踩踏分派器**
(`docs/re/18` 早就記過它)。

同一批字串裡的 `Attack- two three four`,我先前也讀成「連擊次數」。
追下去發現 `two`..`six` 的擁有者是 `sub_20ED0`,而它的呼叫者印的是

```
That will be <N> gold for the <four> of ye, sir.
```

—— **旅店按人頭報價**。`Attack-` 只是在字串池裡排在旁邊而已。

> ⚠ 相鄰的字串不代表相關的功能。字串池的順序是連結器決定的,
> 拿「隔壁那句」推語意就是二手推論(`rulebook/62`)。這一輪兩條 ⬜
> 都是這樣誤標的。

## 2. 每一層養一隻遊蕩怪物

`sub_5150` 的前三件事,順序不能動:

```
1. 睡著的隊員各擲 random(0,63) < 4  → 醒
2. arg_4(這回合有推進時間)→ sub_4C6C():怪物走一步
   走到隊伍腳下 → sub_5008()「遭到襲擊!」→ 開打 → 換一隻新的
3. 才處理腳下那一格(房間 / 陷阱),而且是**重讀**之後才處理
```

第 3 步重讀是因為戰鬥可能把人挪走了。把 2 和 3 對調的話,
玩家會先中陷阱再被襲擊 —— 順序反了,體驗就不一樣。

### 怪物住在物件槽 1,上一格記在物件槽 2

`dword_3E474` = `dword_3E46C + 8` = 物件陣列的第 1 槽;`dword_3E47C` 是第 2 槽。
所以「遊蕩怪物」不是另一套資料結構,它就是一個普通物件,
而第 2 槽被拿來當**它的上一格**。

`[+2]`=x `[+3]`=y `[+4]`=樓層 `[+5]`=生物索引(0xFF = 沒有怪) `[+0]/[+1]`=圖組。

## 3. 八種怪物 = `MON0.16`..`MON7.16`

生成時抽 `random(0,7)`,查 `byte_3F3D0[8]`:

| 圖組 | 索引 | 生物編號 | 名字 | `byte_3F3D8` |
|---|---|---|---|---|
| MON0 | 20 | 144 | Giant Rat 巨鼠 | 0x60 |
| MON1 | 21 | 148 | Bat 蝙蝠 | 0xA0 |
| MON2 | 22 | 152 | Giant Spider 巨蛛 | 0x00 |
| MON3 | 23 | 156 | Ghost 幽魂 | 0x90 |
| MON4 | 24 | 160 | Slime 泥怪 | 0x80 |
| MON5 | 25 | 164 | Gremlin 小鬼 | 0x60 |
| MON6 | **28** | 176 | Gazer 凝視魔 | 0x00 |
| MON7 | **27** | 172 | Reaper 收割者 | 0x00 |

⇒ **`WORKLIST` 上「怪物圖 MON0–7.16(8 組)」為什麼剛好八組,答案在這裡**:
它不是「八組怪物美術」,是**地牢遊蕩怪物的名冊**,圖組索引就是抽到的那個 0..7。

三條獨立佐證:

1. 八個名字全部從 `DATA.OVL` 的生物名表查得出來(測試會擲回原始資料核對),
   而且都是地牢裡合理的怪。
2. **最後兩筆是 28、27,順序反的。** 資料自己不整齊,才證明它是真表而不是我
   照印象填的。
3. `sub_4C6C` 唯一豁免移動的索引是 **0x1B = 27 = Reaper** —— U5 裡它是紮了根的
   樹妖。表要是偏一格,豁免的就會是某種能走的怪物。

`byte_3F3D8` 的語意**未解**。取用它的 `sub_31F0` 只抽 0x90 / 0x60 / 0x0F,
而 0x0F 在這八項全是 0;拿去對 `byte_3F1D0` 的怪物旗標,八項全不合
(例:巨鼠旗標 0x0300 vs 這裡 0x60)。看得出是第一人稱視圖的擺法,
第一人稱透視還沒做,所以照原樣留著不取名字。

## 4. 生成與移動是**兩套不同的通行規則**

```
生(sub_4594):  高四位元 < 0x60,或剛好 0x70(門)
走(sub_4C6C):  高四位元 不是 0x60、不是 0x80、且 < 0xA0
```

⇒ **0x90 走得進去,卻生不出來。** 這不是我抄漏了 —— 兩支的比較式就是不一樣。
0x90 在地牢資料裡還沒有已命名的語意(`DungeonMagic` 是 0x80),
硬把兩條湊成一條會少掉這個行為。

### 落點還會排除隊伍的**整行整列**

```asm
mov  edx, byte_3E0A6   ; 隊伍 X
cmp  edx, esi          ; esi = 落點 X
jz   retry
mov  edx, byte_3E0A7   ; 隊伍 Y
cmp  eax, edx          ; eax = 落點 Y
jz   retry
```

比的是兩個座標**各自**相等,不是「同一格」。所以剛換層時怪物一定不在你的
正前方或正側方 —— **第一步是安全的**。這種「看起來多餘的條件」正是柵欄原則
要重建的那種設計:它擋住了「一進門就被撲」。

八次都找不到落點 → 這一層沒有怪(座標寫 0xFF、生物索引寫 0xFF)。

### 不肯原地踱步

想走回上一格時要再擲一次:

```asm
push 7 ; push 0 ; call sub_28E14   ; random(0,7)
dec  eax
jnz  retry                          ; 只有擲出 1 才准回頭
```

## 5. 「遭到襲擊!」的兩個細節

```asm
mov  al, byte_3EE14     ; 攻擊來向(從怪物的上一格算)
cmp  al, byte_3EE15     ; 隊伍朝向
jz   short loc_50E6     ; 一樣 → 跳過 " from the X"
...
mov  al, byte_3EE14
mov  byte_3EE15, al     ; 轉身面向攻擊者
```

1. **方位只在你沒面對它時才報。** 從你正對著的方向撲上來,原版只說
   「Attacked!」—— 你看得見它,不需要人家告訴你在哪邊。
2. **被襲擊會把隊伍轉過去。** 下一步的「前進」方向因此變了。

`byte_3EE15` 是朝向這件事是由 `sub_4504`(地牢 HUD 的羅盤)獨立確認的:
它把同一個位元組印成 `North`/`East`/`South`/`West`。而寫朝向的 `sub_100F8`
只把 4 / 5(上下樓)寫進 `byte_3EE14`,所以 **`byte_3EE15` 永遠是 0..3**。

方位的算法(`& 7` 是因為一層 8×8 而且**繞回**):

```
隊伍 x == (怪 x − 1) & 7 → 東      隊伍 y == (怪 y − 1) & 7 → 南
隊伍 x == (怪 x + 1) & 7 → 西      其餘                      → 北
```

## 6. ★ 地牢戰場**不在 `DUNGEON.CBT` 裡** —— 它是當場畫的

我一開始在找「地牢遭遇戰讀哪一張 `.CBT`」,差點下「這份資料還沒破」的結論。
真相是 **根本沒有那份資料**:`DUNGEON.CBT` 的 112 張全是房間(7 座 × 16 間),
遊蕩怪物的戰場由 `sub_FE48` → `sub_FD54` 現畫在戰鬥地圖緩衝 `byte_3F8F4` 上。

> 找不到的東西有兩種:還沒找到的,與不存在的。分不清就會把後者寫成前者。

緩衝先被 `rep stosd`(eax = 0xFFFFFFFF)填成 **0xFF**,而 0xFF 在本專案早就是
`TileBlank`「此處無物」(`sceneset.go`)—— 兩邊獨立對上。

### 骨架(`sub_FD54`)

```
列 1 與列 9 整條(x = 0..10)   = 牆
行 1 與行 9 整條(y = 0..10)   = 牆
四角 (0,0) (10,0) (0,10) (10,10) = 0xFF
中央 (5,5)                      = 腳下地形對應的擺設
內部 7×7 與外環                  = 沒寫過 → 留著 0xFF
```

中央的擺設查 `byte_418E0[高四位元 >> 4]`:

| 腳下 | → 中央 |
|---|---|
| 0x10 上行梯 | 0xC8 |
| 0x20 下行梯 | 0xC9 |
| 0x30 兩向梯 | 0xC8(畫成上行) |
| 0x40 寶箱 | 0xDC |
| 0x50 噴泉 | 0xD8 |
| 0x60 陷阱 / 0x70 門 | 無 |

★ 0xC8 / 0xC9 正是本專案早就在用的上下梯 tile,0xDC / 0xD8 對上寶箱與噴泉 ——
**四個值都能獨立對照,位移沒有偏。** 站在寶箱上開打,戰場正中央就有個寶箱。

### 四面牆照你站的路口開口(`sub_FC7C`)

對每個方位去看**地牢裡**那個方位的鄰格:

| 鄰格高四位元 | 那面牆 |
|---|---|
| < 0xA0(通道、梯子、陷阱、門檻…) | 開 **7** 格(`sub_FBF0`) |
| 0xB0 / 0xC0 / 0xD0(牆) | **整條外環抹成 0xFF**(`sub_FAC4`) |
| 其餘(房間 0xA0 / 0xF0、門 0xE0) | 開 **5** 格(`sub_FB6C`) |

⇒ **戰場的形狀就是你剛才站的那個路口。** 死巷裡打就只有一個出口。
少了這一步,戰術完全不同 —— 這是「機制忠於原版」在細節上長什麼樣子。

⚠ 兩個實作陷阱:

- `< 0xA0` 那條之後**沒有 jump**,所以 `sub_FB6C` 的五格也會再跑一次。
  那五格落在同樣的七格裡面,是無效動作 —— 照抄行為,不必照抄冗餘。
- `sub_FAC4` 抹的是 **11×11 的最外一圈**那一整條,跑在框畫好之後,
  所以會蓋掉框在外環上的兩格。我第一版的測試把那兩格當成牆,紅了 ——
  **紅的是預期,不是實作。**

另有兩對寫死的座標:站在門檻(0xE0)上而北面 / 西面被封時,
額外在 (5,2)/(5,8) 或 (2,5)/(8,5) 補牆。語意不明,照抄。

### 入場位置:四張表當八份用

隊伍的入場位置在 352 B 裡按「側」分四組(側 = 第 1/2/3/4 列的 +11 與 +17):

```
側 3(朝北)X = byte_4190A  Y = byte_418FE
側 2(朝東)X = byte_41904  Y = byte_418F8
側 4(朝南)X = byte_418F8  Y = byte_41904
側 1(朝西)X = byte_418FE  Y = byte_4190A
```

`byte_418F8` 與 `byte_4190A` 內容相同({5,4,6,3,5,7});另兩張是
{6,7,7,8,8,8} 與 {4,3,3,2,2,2}。★ **原版沒有存四份座標,存了兩份形狀** ——
四個方位的隊形就是同一個楔形轉 90 度,X 與 Y 互相對調。

敵人的 16 個入場點同理,四張表按朝向兩兩配對,而且
`byte_41920 = 10 − byte_41930` 逐項成立(測試用這條對稱性把表釘住)。

⇒ 這同時解掉 `combatmap.go` 裡留了很久的那條註記:
「列 1、2、4、5 各有一批沒解出來的資料,格式看起來像另一種入場方向」——
**就是四個入場方向**。本專案原本只用列 3(`combatPartyX = 107 = 3×32+11`),
也就是永遠當成「朝北入場」。

### 牆與地板依地牢不同

`sub_5378`:地牢編號(地點 − 0x20)為 **1 / 4 / 5** 的三座用一組,其餘七座用另一組,
而且前者另外把圖組換成 `byte_3EE16 = 3`。

| 編號 | 對照 `DungeonEntrances` | 牆 | 地板 |
|---|---|---|---|
| 1 / 4 / 5 | 索引 0 / 3 / 4 = **欺瞞、謬誤、貪婪** | 0x4F | 0x45 |
| 其餘 | | 0x4D | 0x05 |

名字是查一手表得到的(`DungeonEntrances` 同樣抽自執行檔),不是憑習慣順序推的。

### 隻數與站位

```
洗牌 0..15(Fisher-Yates,random(0,15))
n = random(1, 群體上限)              ; 群體上限 = 怪物屬性表 byte +6(GroupMax)
if 群體上限 == 8 或 16 → n = 群體上限  ; 這兩個值直接出滿
前 n 個洗過的槽填上 生物索引×4 + 0x40
```

⇒ **同一種怪物每次的站位都不一樣**。而且地牢這條路徑**沒有混編** ——
地表遭遇會有 1/9 機率換成 `CreatureMix` 指定的另一種,地牢不會。

## 8. 還沒做的

- ⬜ **另一種戰場**(`byte_3E0B1 & 4`):中央擺 0xB3、四個側都用
  `byte_418E8`/`byte_418F0`、敵人用 `byte_41950`/`byte_41960`、
  而且怪物種類**重抽**而不是沿用遭遇到的那隻。由 0x2BB80 附近那條路徑觸發,
  觸發條件還沒追。地牢遊蕩怪物走的是 `byte_3E0B1 = 2`,不吃這條。
- ⬜ 第一人稱透視下這隻怪物怎麼畫(`sub_31F0` + `byte_3F3D8` 的語意)。
- ⬜ `sub_10334` 的 `arg_4 == 1`/`3` 兩條(房間戰鬥走的是 3),
  與這裡的 2 共用同一支但走不同分支。房間目前用 `DUNGEON.CBT` 的現成圖,
  沒有走這條 —— 兩者是否一致還沒比對。
- ⬜ 戰場的 0xFF 在畫面上長什麼樣(留白?畫成地牢地板?)。這是**呈現**問題,
  要對 DOSBox 實機截圖才有答案(`rulebook/65`),機制不受影響。

## 附:那「另一種戰場」是**紮營**(2026-08-08 追加)

§8 列了一項未完:`byte_3E0B1 & 4` 的第二種戰場,「觸發條件還沒追」。
追指令表時撞到了答案 —— `sub_2B8CC`(Hole up)的尾巴:

```asm
cmp  byte_3E0A3, 20h        ; 地牢?
jbe  short loc_2BB9E
mov  byte_3E0B1, 6          ; ★ 6 & 4 = 4 → 第二種戰場
call sub_102B4
call sub_FE48
push [ebp+var_C]            ; 睡幾小時
push [ebp+var_8]            ; 守夜的人(−1 = 無人)
movzx eax, byte_3E0B1
call sub_2E364
...
loc_2BB9E:                  ; 地表
push [ebp+var_C]
push [ebp+var_8]
call sub_2E8B0              ; → sub_2E51C(0) + sub_2E364(4, 守夜, 時數)
```

⇒ **紮營就是進一個專用戰場**:地表用模式 4、地牢用模式 6。所以那組
`byte_418E8`/`byte_418F0`(隊伍散開的位置)與 `byte_41950`/`byte_41960`
(敵人位置)畫的是**營火四周的隊形**,而「怪物種類重抽而不是沿用遭遇到的那隻」
也就說得通了 —— 紮營時本來就沒有「遭遇到的那隻」,是野獸自己找上來。

⬜ 仍未做:`sub_165C8`(模式 4 的解算)—— 要不要被襲擊、守夜的人有沒有發現。
`internal/game/holeup.go` 目前紮營一定睡得安穩,並在該處標明是已知落差。
