# 63 — FM Towns 的 25 個 `.SND`:sign-magnitude 有證據了

| | |
|---|---|
| 輸入檔 | `U5_E/*.SND`(25 個,566 B .. 66,390 B)、`U5_E/U5_SE.TBL`(純文字) |
| 落地 | `internal/u5data/snd.go`、`u5dump snd <U5_E> <輸出目錄>` |
| 相關 | `CLAUDE.md` §2.4 早就記著「`.SND` 是 sign-magnitude PCM,不是二補數」 |

## 檔頭 32 B

```
+0x00  8 B   名字(ASCII,NUL 填滿)  "Take1" "Clock2" "BariBari" "funsui2" …
+0x08  u32   0x1EF6 = 7926           ← 24 / 25 個檔案相同
+0x0C  u32   **資料長度** = 檔案大小 − 32
+0x10  u32   見下面「像迴圈但沒全對」
+0x14  u32   同上
+0x18  u32   1960 / 1568 / 1586(語意未解)
+0x1C  u32   60 / 61(語意未解)
```

`+0x0C` 對 **25 / 25** 個檔案都正好等於「檔案大小 − 32」—— 檔頭長度不必猜。

⚠ 名字欄位**會溢出**:`SUITEKI3.SND` 的名字寫成 `suiteki2suit`(12 B),
把 `+0x08` 的常數蓋掉了。所以**不要拿 `+0x08` 當 magic 驗檔**;
要驗就驗 `+0x0C` 與檔案大小的關係。

## 第二份獨立佐證:`U5_SE.TBL` 是純文字表

```
WALK.SND 100 3032
WALKSLOW.SND 100 3032
HORSE.SND 100 6432
…
FUNSUI2.SND 20 60032
```

每行 `檔名 音量 檔案大小`,23 行(`BEEP.SND` 與 `BARIBARI.SND` 沒列)。
**第三欄與實際檔案大小逐一相符** —— 這與 `+0x0C` 是兩個獨立來源,
一起把 32 B 檔頭釘死。第二欄是音量 0..127,而且看得出用心:

| 音量 | 音效 |
|---|---|
| 127 | 鐘擺、鏡子、水滴、死亡 |
| 100 | 腳步、馬、格擋、攻擊、受傷…(多數) |
| 88 | 警報 |
| 80 | 魔法、月門、瀑布 |
| **20** | **噴泉** ← 一直在響的環境音,刻意壓得很低 |

⚠ 表裡的檔名大小寫**不一定**與實際檔案相同(表寫 `Fire.SND`,檔案是 `FIRE.SND`)。
⚠ 檔尾有一個 `0x1A`(DOS 的 Ctrl-Z EOF 標記)—— 當年的文字檔慣例,不切掉會解析失敗。

## PCM 是 sign-magnitude —— 這次有量化證據

`knowledge-base` 早就記著這個陷阱,但沒有留下判斷方法。這次用「相鄰取樣的
**平均絕對差**」當平滑度指標,對十個檔案分別用三種解讀跑一遍:

| 檔案 | sign-magnitude | 二補數 | 無號 −128 |
|---|---:|---:|---:|
| ALARM3 | **1.16** | 8.20 | 8.18 |
| ATTACK1 | **4.78** | 10.94 | 11.06 |
| BEEP | **0.39** | 1.45 | 1.45 |
| CLOCK2 | **1.42** | 29.93 | 30.11 |
| DAME1 | **11.30** | 34.73 | 34.28 |
| DEATH1 | **7.53** | 36.56 | 36.64 |
| **合計(10 檔)** | **43.0** | 162.2 | 162.0 |

**十個檔案全部 sign-magnitude 勝**,合計差 3.8 倍。原因很直觀:二補數解讀會把
`0x80..0xFF`(在 sign-magnitude 裡是**小的負值**)變成極大的負值,
於是波形每次過零就跳一次 —— 聽起來是滿滿的雜訊,一秒就分辨得出來。

`sndSample`:bit 7 是正負號、bit 0..6 是大小,所以 **`0x00` 與 `0x80` 都是靜音**。
`TestSoundPCMIsSignMagnitudeNotTwosComplement` 對**每一個**檔案跑這個比較,
不是抽樣。

## `+0x10` / `+0x14`:像迴圈,但**沒有全對**

三個檔案的兩欄相加正好等於全長,而它們剛好就是該迴圈的那三個環境音:

| 檔案 | +0x10 | +0x14 | 和 | 全長 |
|---|---:|---:|---:|---:|
| `FUNSUI2`(噴泉) | 0 | 60000 | 60000 | 60000 ✓ |
| `TAKI2`(瀑布) | 38839 | 21161 | 60000 | 60000 ✓ |
| `BARIBARI`(電光) | 51367 | 14991 | 66358 | 66358 ✓ |

算術與語意同時對上,很難是巧合。**但其餘檔案套不進去**:

| 形態 | +0x10 | +0x14 | 檔案 |
|---|---|---|---|
| 多數一次性音效 | 全長 − 1 | 0 | `ALARM3` `WALK` `ATTACK1` … |
| 尾巴一個取樣 | 全長 − 1 | **1** | `BEEP` `SUITEKI3` |
| 兩個都 0 | 0 | 0 | `DOKU` `MAHOU1` |

一個取樣的迴圈沒有意義,而 `0 / 0` 也解釋不了。

⇒ **這個讀法還不算解出來。** 兩個欄位原樣保留在 `LoopStart` / `LoopLen`
(解析器**不做任何「修正」**),`Loops()` 用的是**明說的判準**:
長度 > 1 且起點 + 長度 == 全長。它剛好挑出那三個環境音 ——
但那是依據三個檔案的語意所下的讀法,不是證明。
日後若被推翻,只要改 `Loops()` 一個函式,不必回頭懷疑解析器動過手腳。

## 取樣率也還沒定案

`+0x08` 的 7926 是唯一像取樣率的數字,而照它算出來的長度都合理:

| 音效 | 取樣數 | @7926 Hz |
|---|---:|---:|
| `CLOCK2`(滴答) | 534 | 0.07 s |
| `NIGE`(逃) | 1100 | 0.14 s |
| `WALK`(腳步) | 3000 | 0.38 s |
| `BEEP` | 4000 | 0.50 s |
| `FUNSUI2`(噴泉) | 60000 | 7.57 s |
| `MAHOU1`(魔法) | 66172 | 8.35 s |

全部落在該有的範圍。但**沒有第二個來源佐證**,所以常數叫 `SndAssumedRate`
—— 名字裡的 Assumed 是刻意的。要定案得逆 FM Towns 的音源驅動,
或拿實機 / 模擬器的音訊 A/B 比對。

## 驗收

`u5dump snd <U5_E 目錄> <輸出目錄>` 產出 23 個 WAV,**用耳朵聽**。
波形的健全性也可以量:峰值與靜音比例都像真音訊
(`CLOCK2` 峰值只有 10、靜音 29% —— 一個很輕的滴答;`ATTACK2` 峰值 114)。

⚠ 轉出的 WAV 與原始 `.SND` **都不入庫**(版權素材,`re_work/` 已 gitignore)。
