## 1. 問題

`docs/re/33` §6 留下一條:**檀香木盒擺在哪裡還沒找到**。它是真結局的前提
(沒有盒子,王座廳那一幕只有壞結局那條分支),所以這不是收尾的小事。

找過而且落空的地方:`BRIT.OOL` / `UNDER.OOL`、`DUNGEON.CBT` 的怪物槽、
地表與地牢兩張獎品表、`INIT.GAM` 的開場旗標。

## 2. 三條線索接起來

**(1) 對話。** 全檔搜 "sandalwood",命中在 `CASTLE.TLK` 0xE1C ——
bit7 編碼的明文,第 7 筆記錄(offset 0xD5B,index 8),說話的是
**Saduj**(a shifty-eyed man):

> `...rests a sandalwood box.` … `Blackthorn himself sent [me] … object hidden [in] British's chambers.`

⇒ 東西在不列顛王的城堡裡。

**(2) 地圖。** 城堡是地點 17,`SceneIndex = 1`,所以二樓 = `CASTLE.DAT`
場景 **3**。那一帶長這樣(x = 13..21):

```
y=11  4F 4F 4F 4F 4F 4F 4F 45 50
y=12  AE 93 44 4F 44 44 4F 45 50      ← (17,12) (18,12) 是地板,四周全是牆
y=13  4F 4F BC 4F 4F 4F 4F 45 50      ← (17,13) 石牆 0x4F ← 豎琴切換的就是這一格
y=14  5D 44 44 44 44 FB 4F 45 50
…
y=17  44 44 44 44 92 44 4F 45 50      ← (17,17) 椅子
y=18  AC 4F 44 4F 8D 5B 4F 45 50      ← (17,18) 豎琴
```

`0x4F ^ 0x0B = 0x44` —— 石牆 ⇄ 地板。`docs/re/35` 解出來的那個 XOR,
開的就是這間 2 格密室的門。**而豎琴 (17,18)、椅子 (17,17)、暗門 (17,13)、
密室 (17,12) 在同一條 x = 17 的直線上。**

> ⚠ 走錯過一次:先把二樓算成場景 **4**,於是讀到 `0x05 ^ 0x0B = 0x0E`
> ——「草地變成另一種草地」,怎麼看都不像暗門,差點回頭去推翻 `docs/re/35`。
> 錯因是把 `SceneIndex` 當成 0 而不是 1。**地點 17 有地下層,起始索引不是 0。**
> 教訓:算出來的東西講不通時,先回去驗算式的輸入,不要先懷疑結論。

**(3) NPC 檔。** `CASTLE.NPC` 地點 17 的生物編號陣列:

```
00 70 70 70 70 70 70 70 70 70 70 70 70 5C 50 10 11 11 68 50 68 48 1B 01 01 01 50 70 1E 58 54 0E
                                                                                              ↑ 槽 31
```

**槽 31 生物編號 `0x0E`,排程三格全是 (18, 12) 樓層 2,四個時刻全 0。**
`0x0E` 正是 `sub_154BC` 的檀香木盒種類碼。

把 `0x0E` 與 `0x10E` 並排切出來看:`0x0E` 是草地,**`0x10E` 是一只白底紅帶的木盒**
—— NPC 的圖在 `NPCTileBase + 生物編號`,盒子也走同一條(`docs/screenshots/21-sandalwood.png`)。

## 3. 一個 tile 怎麼變成 Get 撿得起來的東西

`sub_15A94`(Get)掃的是**物件表** `dword_3E46C`,不是 NPC 表。
所以還缺一環。答案在 `sub_1E74`:

```
sub_1E74(npc, x, y, floor):
    if (byte_3EDB0[npc] == 0) return;              // 空槽
    rec = &word_3E770[npc*16]                      // 執行期 NPC 記錄
    if (目前樓層 != floor && rec[+0xC] != 0) {      // 換層了 → 放掉槽
        dword_3E46C[rec[+0xC]*8] = 0
        rec[+0xC] = 0
    }
    if (目前樓層 == floor && rec[+0xC] == 0) {      // 在本層又沒槽 → 配一個
        slot = sub_2B57C()                          // 找空槽
        品質 = (生物編號 == 1)              ? 0x1E
             : (off_4FC98[地點] >> npc & 1) ? 0xFF
             :                                0
        sub_2B6C8(生物編號, 生物編號, x, y, floor, 品質, slot)
        dword_3E470+2[slot*8] = 0
        rec[+0xC] = slot
    }
```

⇒ **每個「此刻在本層」的 NPC 都在物件表佔一格**,`word_3E77C`(記錄的 +0xC)
記住配到哪一槽。反向查詢是 `sub_2E0`,移除是 `sub_268`(清兩張表)+
`sub_218`(把位元寫進 `dword_3E368[地點]`,存檔帶得走)。

這條鏡射解釋了三件原本各自懸著的事:

| 現象 | 因為 |
|---|---|
| 城裡的寶箱能開 | 生物編號 1 的 NPC 槽 → 物件種類 1,品質 0x1E |
| 地上的物品撿得起來 | 生物編號 < 0x10 的 NPC 槽 → `GetPickable` 收 |
| Get 掃到人不會停 | 人也佔槽,種類 ≥ 0x40 過不了四個條件,**繼續往下掃** |

★ 品質 **0x1E = 30**,正好是地表寶箱擲獎 `random(1, 30)` 的上限
(`docs/re/33` §4)。兩個數字從不同函式獨立得出而對上,`ObjQuality` 這個
欄位解讀就再確認了一次 —— 也順手推翻 `objects.go` 原本寫的
「+5..+7 全檔沒有其他讀寫處」。

### `off_4FC98`:照抄,但不賦予語意

`test off_4FC98[地點*4], (1 << npc)` 命中就給品質 0xFF。整張表只有四個地點非零:

| 地點 | 遮罩 | 槽 | 生物編號 |
|---|---|---|---|
| 4 紫杉城 | 0x00028000 | 15, 17 | 0x90(都在地下層) |
| 5 米諾克 | 0x00000002 | 1 | 0x48 |
| 28 溫德米爾 | 0x000003F8 | 3..9 | 0x90 |
| 29 石門 | 0x000001E0 | 5..8 | 0x94(城堡四角) |

全是怪物。**品質欄在怪物身上代表什麼還沒有證據**,所以只照抄數值。

⚠ 索引 0 讀到的是 `0x47924` —— 那是字串 `"cowardice"` 的位址。
`off_4FC98` 與碎片名指標表 `off_4FC90` 重疊(`0x4FC98 = 0x4FC90 + 2×4`),
第 0 格根本不是遮罩。大地圖不走這條路,讀不到,但**別把它當成資料**。
(順帶:`off_4FC90` = `falsehood` / `hatred` / `cowardice`,獨立確認了
`docs/re/33` §7 的三塊碎片順序。)

## 4. 樓層位元組是有號的

追這條時撞到另一個 bug:`.NPC` 排程的樓層欄 **0xFF 是 −1**,與
`Location.SceneOffset` 用的是同一條規則,而執行期狀態沒有轉換。

後果:不列顛王城堡地下室的三個寶箱(槽 23/24/25,樓層 0xFF)拿 255 去跟
樓層 −1 比,永遠不相等 —— **整層的東西一個都不出現**。
畫面上是一間空房,看起來完全不像 bug。

修法是 `u5data.SignedFloor()`,四處讀樓層的地方全部改走它。

## 5. 於是整條路通了

```
Saduj 說盒子在王的寢宮
  → 二樓 (17,18) 有豎琴,(17,17) 有椅子
  → 坐下彈 6 7 8 9 8 7 8 7 6 7 6 5 3
  → (17,13) 石牆 0x4F ^ 0x0B = 地板 0x44
  → 走進 2 格密室,盒子在 (18,12)
  → Get 東 → sub_154BC 種類 0x0E → SandalwoodBox = true
  → 王座廳那一幕走真結局那條分支
```

整合測試 `TestTheSandalwoodBoxBehindTheHarpDoor` 用**真的原版資料**跑完這一條,
因為它要驗的正是三個檔案彼此對得上:`CASTLE.TLK` 的線索、`CASTLE.DAT` 的牆、
`CASTLE.NPC` 的盒子。截圖:`docs/screenshots/21-sandalwood.png`。

## 6. 與原版的一處刻意差異

原版連人也鏡射進物件表,而且畫面就是照物件表畫的。本引擎的人另有一條
算繪路徑(`VisibleNPCs`,帶朝向與逐格移動),所以鏡射出來的槽在
`VisibleObjects` 會被跳過,免得同一格畫兩次。

**鏡射本身照抄(人也配槽)** —— 因為 Get 的「掃到不可撿的就往下一槽」
這個行為要有那些槽在場才成立。差異只在誰負責畫。

## 7. 這一份的教訓

- **算出來的東西講不通時,先驗算式的輸入。** 場景索引差 1,結論就從
  「石牆變地板」變成「草地變草地」,而我第一反應是懷疑 `docs/re/35` 的 XOR。
- **空結果要驗掃描本身。** 第一次掃 `.NPC` 找生物編號 0x0E 掃了整個檔案而不是
  每個 576 B 區塊的 `+0x200` 那 32 個位元組,得到零命中,於是繞去讀
  `sub_1678` 的場景載入路徑找不存在的「tile → 物件」掃描。
  正確的掃法一次就命中(`diagnosis-notes/02`:回空之前先做正對照)。
- **兩個獨立來源對上才算數。** 盒子的位置由 `CASTLE.NPC`(槽 31 → (18,12))
  與 `CASTLE.DAT`(那兩格是牆圍起來的地板)分別給出,加上 `CASTLE.TLK`
  的文字線索 —— 三份檔案互相印證,不是從一處推論出來的。
