## 1. 引擎的 Ready 是「查編號範圍 → 塞進去 → 舊的放回背包」

原版有一整套前置檢查,每一條都有自己的拒絕訊息。漏掉的後果不是崩潰,
是**遊戲變簡單了** —— 而那種差異沒有任何測試看得出來。

| 原版的規則 | 引擎原本 |
|---|---|
| 同一鍵按在身上那件 = **卸下** | 沒有這一步 |
| 部位有東西 → **拒絕**(五句訊息) | **默默替換**,舊的丟回背包 |
| 雙手武器要**兩手都空** | 沒有雙手概念 |
| 拿著雙手武器時左手也不能用 | 同上 |
| 六格重量加總 + 新件 > 力量 → **拒絕** | 沒有重量概念 |
| 弓沒箭 / 十字弓沒弩矢 → **拒絕** | 沒有 |
| 箭與弩矢**本身裝不上** | 當成一般裝備 |
| 戰鬥中不能換護甲(除非勝負已定) | 沒有 |
| 戴上兩種魔法戒指時 1/16 消失 | 沒有 |

## 2. 兩張 48 筆的表

原版**不用編號範圍**判部位,而是查 `byte_40BD4[裝備編號]`。
IDA 把它拆成 `db` / 字串 / `dw` / `dd` 混排(0x20 是空白、0x30 是 `'0'`、0x40 是 `'@'`,
整段被當成字串了):

```
byte_40BD4  db 4 dup(80h)
a000        db '     @@@@@@@ 0 0      0',0
a0_0        db '0',0
            dw 3020h
            dd 30303030h, 20202030h, 2023020h, 4040402h
```

逐段展開 = 4 + 24 + 2 + 2 + 16 = **48 筆**,與 `ItemCount` 相同。

```
0..3    0x80 頭盔          9..15   0x40 護甲
4..8    0x20 單手(盾)     42..44  0x02 戒指        45..47  0x04 頸飾
16..41  0x20 / 0x30 交錯 —— 除了 27 與 29 是 0x00
```

### ★ 為什麼一定要用表:區間表達不出「雙手」

單手(0x20)與雙手(0x30)在編號上是**交錯**的:16 單、17 雙、18 單、19 雙、
20..25 單、26 雙、28 雙、30 單、31..36 雙、37..40 單、41 雙。
`ItemWeaponFirst..Last` 那種區間永遠推不出來。
`TestOneAndTwoHandedWeaponsInterleave` 把交錯本身釘住 ——
交錯一旦成立,區間法就沒有存在的餘地。

### ★★ 三條證據指向同一對編號:27 與 29 是彈藥

1. 展開後**只有兩筆** 0x00:編號 27 與 29。
2. `sub_1EC34` 的第一件事:`if (item == 1Bh || item == 1Dh) return 0`(**無訊息**)。
3. 弓(0x1A)與魔法弓(0x24)裝備前查 `byte_3DFEB`、十字弓(0x1C)查 `byte_3DFED`,
   而那兩個位址換算回存檔正是 `Items[27]` / `Items[29]`
   (換算用同區的錨 `byte_3DFD0 ↔ SaveItemsOffset 0x021A`)。

而 `u5data/items.go` 早就寫著 `ItemArrows = 27` / `ItemQuarrels = 29`。
⇒ **箭與弩矢不是裝備,是彈藥**:沒有部位、裝不上,只被弓查詢。

## 3. ★ 重量表最強的一個 oracle:15 名預設角色全部背得動自己的裝備

重量在 `byte_40C04`(48 筆)。規則:

```asm
edi = 0
for (i = 0; i < 6; i++)                    ; +0x19..+0x1E 六格
    if (裝備[i] != 0FFh) edi += byte_40C04[裝備[i]]
ecx = edi + byte_40C04[新件]
al  = (byte_3DDC0[who*32] >= ecx)          ; ★ 力量,setnl → 是 >= 不是 >
```

把它拿去跑 `INIT.GAM` 的 15 名預設角色:

| 角色 | 職業 | 力量 | 裝備重量 |
|---|---|---|---|
| Shamino | F | 20 | 11 |
| Iolo | B | 19 | 10 |
| Mariah | M | 12 | 1 |
| **Geoffrey** | F | **24** | **20** |
| Jaana | M | 15 | 1 |
| Julia | B | 21 | 7 |
| **Dupre** | F | **22** | **21** |
| Katrina | F | 22 | 3 |
| Sentri | F | 23 | 9 |
| Gwenno | B | 17 | 4 |
| Johne | M | 14 | 3 |
| Gorn | F | 21 | 14 |
| Maxwell | F | 21 | 11 |
| Toshi | B | 17 | 3 |
| **Saduj** | B | **21** | **16** |

**15/15 不超標,而且三個貼著上限。** 若那 48 個數字裡有一格抄錯、
或「六格加總」這條規則讀錯,幾乎一定有人會超。
⇒ 這條測試不是在驗程式碼,是在驗**我抄的數字**
(`TestStartingRosterCanCarryItsOwnEquipment`,並額外要求「至少有人貼近上限」——
不然重量表整排填 0 也會過關)。

## 4. 空手狀況 `sub_1EBE8` 的第四個分支

```
兩手都空                                        → 2  (原版接著把 2 改成 0 → 用右手)
右手空                                          → 0  (右手)
右手有東西、左手空、而右手那件**不是雙手武器**  → 1  (左手)
其餘                                            → 0xFF → "Thou must free one of thy hands first!"
```

★ 第三個分支的後半是重點:**拿著雙手武器時,左手欄位是空的卻不能再拿東西**。
`TestTwoHandedWeaponsNeedBothHands` 的後半段專驗這條 —— 它也是「用編號區間
寫不出來」的第二個例子。

雙手武器記在**右手**那一格(`byte_3DDCF` = `CharWeapon`),左手保持空。

## 5. 戰鬥中換護甲的閘門是 `byte_3E0B3`,而它是「勝負已定」

```asm
if (9 <= item <= 0Fh && byte_3E0A3 > 7Fh && byte_3E0B3 == 0)
    → "Thou canst not change armour in heated battle!"
```

`byte_3E0B3` 的來源在 `sub_A9EC`(戰鬥主迴圈):開戰時 `word_3E086 == 0` 就設 1、
否則設 0;而 `VICTORY!` 與 `BATTLE IS LOST!` **都只在它為 0 時印**,印完 victory
還把它設成 1。⇒ 它是「這場戰鬥的勝負已定 / 不是真的戰鬥」,一次性訊息的閘門。

⇒ **勝負已定之後在戰場上是可以換甲的**,而武器一直都換得了 —— 那條規則只管護甲。

## 6. ★★ 順帶推翻 `docs/re/53` §2:戰場上的隊員圖**依職業**

### 上一輪的結論

`docs/re/53` §2 斷言:

> **與職業無關。** 原版在戰場上只有兩個值:站著 0x1D、躺著 0x1E。
> 我原本以為是照職業選 sprite,那是把「城鎮 NPC 依生物編號選圖」的規則套過來的。

根據是 `sub_2ED50`(起身)與 `sub_2EDF8`(躺下)這兩支成對的函式,而它們寫的是
物件記錄的 **`+1`**。

### 讀 `sub_1EC34` 時撞到第三處寫同一個欄位的地方

```asm
idx = sub_28F5C("AMBFDTPRS", 角色.職業字母)     ; 職業字母 → 0..8
al  = byte_40C34[idx]
物件[+1] = al ; 物件[+0] = al                    ; ★ 兩個位元組都寫
```

順著 `byte_40C34` 的三個讀取點回查,`sub_C414+1D0` 就是**開戰佈陣的迴圈**
(同一圈裡還寫 `+2` 旗標與 `+3` 名冊索引)。表本身同樣被 IDA 拆成 `db` + 字串:

```
byte_40C34  db 4Ch
aDhlllll    db '@DHLLLLL',0
```

= `4C 40 44 48 4C 4C 4C 4C 4C`,九筆,對上九個職業字母:

| 職業 | 圖 |
|---|---|
| A 聖者 | 0x4C |
| M 法師 | **0x40** |
| B 吟遊詩人 | **0x44** |
| F 戰士 | **0x48** |
| D 德魯伊 / T 工匠 / P 聖騎士 / R 遊俠 / S 牧羊人 | 0x4C |

只有四種原型有專屬圖,與 U4 的美術規模一致。
0x1D / 0x1E 只出現在**恢復路徑**上:醒來、躺下、戴上隱形戒指。

### ★ 而 0x4C 正是上一輪「修掉」的那個值

`docs/re/52` §5 記過一個矛盾:

> `sub_16058`(戰鬥中的 Klimb)判「爬得過去」用的是 tile 0x4C,
> 而本專案 `partyTileFor()` 回的也是 0x4C。兩者衝突,而 `partyTileFor`
> 當初是猜的。⬜ 待查。**先不動它**。

`docs/re/53` 回頭追,結論是「0x4C 那邊沒有依據,所以動那一邊」,
把 `partyTileFor` 改成 0x1D / 0x1E。**方向錯了**:
`sub_16058` 拿 0x4C 判「爬得過去」,正是因為**那一格站著隊員**。
原本那個猜是對的。

### 教訓

不是「不該回頭追矛盾」——追是對的。錯在**判斷「哪一邊有證據」時,
用的是「我手上這兩支函式」而不是全檔掃描**。當時只讀了寫 `+1` 的兩支,
沒問「還有誰寫這個欄位」。

`CLAUDE.md` §4.5 已經有一條:

> **「唯一」「只有一處」沒有全檔掃描佐證就不要寫。**

`docs/re/53` 寫的是「原版只有兩個值」—— 那是同一類斷言,而它沒有做那個掃描。
⇒ 那條規則要擴充:**「只有 N 個」「與 X 無關」與「唯一」是同一類斷言,
一律需要全檔掃描。**

## 7. 卸下隱形戒指要做四件事

```asm
sub_2F35C(who, item)                         ; 清那一格
if (byte_3DFD0[item] < 63h) byte_3DFD0[item]++  ; 背包 +1,上限 99
if (地點 > 7Fh && item == 2Ah) {
    物件.tile = byte_40C34[職業]             ; ① 恢復職業圖
    unit.flags &= ~10h                       ; ② 清 UnitHidden
    byte_3DDD1[who] = 0FFh                   ; ③ 戒指欄清空(與上面重複,原版寫了兩次)
    byte_3E0B2 &= ~10h                       ; ④ 那個未解的位元
    for (esi = 31; esi > 5; esi--)
        unit[esi].flags &= ~2                ; ⑤ ★ 清掉所有怪物的「逃跑」旗標
}
```

★ ⑤ 最反直覺:**你現形了,怪物就沒有理由繼續亂跑**。
隱形會讓怪物逃跑(`UnitFleeing`),這是它的反向。迴圈從 31 數到 6 ——
只掃敵人槽,不動隊員的逃跑旗標。

## 8. 兩顆不同的戒指骰子

| | 時機 | 骰值 | 出處 |
|---|---|---|---|
| 穿戴那一次 | `Ready` 寫進欄位之後 | `random(0,15) == **0**` | `sub_1EC34`(本篇) |
| 每場戰鬥開始 | 開戰佈陣的迴圈裡 | `random(0,15) == **11**` | `sub_2EE84`(`docs/re/70`) |

對象相同(隱形戒指 0x2A、再生戒指 0x2C ——**防護戒指 0x2B 不會消失**)、
機率相同,**骰值不同** ⇒ 兩顆骰子,不能合併成一支函式。
`TestRingVanishesOnWearingIsADifferentDieFromCombatStart` 開頭就先斷言
`RingVanishHit != 0`,免得日後有人把兩者「統一」掉。

## 9. 三條被反轉的測試

| 測試 | 原本釘住的 | 現在 |
|---|---|---|
| `TestEquipReturnsTheOldItem` | 「換下來的要放回背包」= **自動替換** | 改名 `TestReadyRefusesWhenTheSlotIsTakenAndTakesOffInstead`:滿了要拒絕、同一鍵卸下 |
| `TestPartyBattlefieldTileIsNotTheClimbable` | 「隊員的圖**不是** 0x4C」 | 改名 `…ComesFromTheClassTable`:九個職業逐一對表,且要求聖者那格**正是** `CombatClimbable` |
| `TestReadyTakesEveryCategory` | 六類都收得下(靠自動替換) | 每類先清空那一格再測 |

★ 第一條是本專案**第四次**踩到「測試在量自己的發明」——
而它的註解還寫著「少了這一步,玩家換一次裝備就永久失去原本那件」。
那個顧慮是真的,只是原版用「拒絕」解決,不是用「放回背包」解決。

另外兩條測試(`TestSecondWeaponGoesToTheOffHand`、`TestReadyMenuChainsTwoPicks`)
是**真紅但原因在別處**:新加的力量規則讓建角角色(皮盔 1 + 鏈甲 10 + 短劍 5 = 16,
力量 20)再拿一件就超重,失敗訊息變成「武器沒裝上」/「汝力有不足!」,
看起來像左手規則或選單壞了。兩條都加了註解說明,並在測試裡先卸掉盔甲。
**這個形狀(失敗訊息指向結果,原因在前置條件)本專案已經第四次遇到。**

## 10. 還沒讀的

- ⬜ `byte_3E0B2` 的 **0x10** 位元:`docs/re/67` §五定出五個位元的四個
  (0x01 killed / 0x02 vanishes / 0x04 slept / 0x08 中毒 / 0x20 grazed),
  0x10 仍未解。卸下隱形戒指時要清它 —— **時機知道了,語意還沒有**。
  引擎沒有這個欄位,所以那一行先不補(補一個假欄位比缺一行糟)。
- ⬜ 物件記錄的 `+0`(種類)在引擎裡沒有對應欄位。原版換圖時 `+0` 與 `+1`
  寫同一個值,而 `+0 >= 0x40` 是「這是生物」的判準(`docs/re/11`)——
  把隊員的 `+0` 寫成 0x4C 之後有沒有別的程式碼因此改變行為,未驗。
- ⬜ `sub_2F35C`(卸下)當黑盒:只知道它清那一格,是否另有副作用未讀。
- ⬜ `sub_28F5C("AMBFDTPRS", ch)` 找不到時回 −1,原版接著讀 `byte_40C34[-1]`
  = 表前一個位元組。引擎不照抄這個越界讀(改用聖者那一格),
  但「什麼情況下職業字母會不在那九個裡」未查。
