# 存檔格式 `SAVED.GAM` / `INIT.GAM`(4,192 B)

> 來源:FM Towns `WORRIORS.EXP` 的 `sub_27D24`(讀)與 `sub_284CC`(寫)。

存檔**不是**一整塊記憶體 dump,而是**逐欄位循序**讀寫一串全域變數:
44 次 `fread`(`sub_377A4`)+ 82 次 `fgetc`(`sub_3806C`),寫入端完全對稱。
所以檔案位移要把每個欄位的大小累加起來算 —— 目的位址之間有空隙,不能直接拿位址相減。

## 34 位元組的落差

FM Towns 的讀取序列加起來是 **4,226** B,而 DOS 與 FM Towns 附的存檔都是 **4,192** B。
拿掉兩樣東西就正好對上,而且最後一個欄位剛好收在 EOF:

- `byte_3EDB0`(32 B)在 FM Towns 版被**連續讀了兩次**(組語確認,不是反編譯錯覺)
- 結尾多一個 2 B 欄位 `byte_3EE18`

32 + 2 = 34。「最後一個欄位剛好收在 EOF」是這個判斷的主要證據 —— 若是隨便挑兩個欄位
湊數字,尾端不會這麼剛好。隨遊戲附的 `SAVED.GAM`/`INIT.GAM` 是 DOS 版寫的
(FM Towns 的資料檔與 DOS 版逐一同大小),所以引擎用 **4,192 的 DOS 版面**。

## 已驗證的位移

| 位移 | 內容 | 驗證方式 |
|---|---|---|
| 0x0002 | **角色名冊**:16 筆 × 32 B | INIT.GAM 讀出 Shamino / Iolo / Mariah / Geoffrey / Jaana |
| 0x02B5 | 隊伍人數 | 3(`sub_1BB5C` 用 `cmp byte_3E06B, 6` 判滿員) |
| 0x02CE | 年(u16) | **139** —— 不列顛尼亞的紀年 |
| 0x02D4 | 時間狀態 | `'T'` 停止時間、`'Q'` 速度加倍(`sub_29304`) |
| 0x02D6 | 載具 tile | **0x1C**,與隊伍的生物編號相符 |
| 0x02D7 / D8 / D9 / DB | 月 / 日 / 時 / 分 | 4 月 5 日 08:35 |
| 0x02E2 | 業報 | 75(對話 opcode 0x89/0x8A 動的就是它) |
| 0x02ED / EF / F0 / F1 | 地點 / 樓層 / X / Y | IOLO'S HUT 第 0 層 (15,15) |

## 角色紀錄(32 B)

| 位移 | 內容 |
|---|---|
| 0x00–0x08 | 名字(9 B,NUL 補齊) |
| 0x09 | 性別:0x0B 男 / 0x0C 女 |
| 0x0A | 職業:`A` 聖者 / `F` 戰士 / `B` 吟遊詩人 / `M` 法師 |
| 0x0B | 狀態:`G` 良好 |
| 0x0C–0x0E | 力 / 敏 / 智 |
| 0x0F | 目前魔力 |
| 0x10–0x11 | 目前 HP(u16 LE) |
| 0x12–0x13 | 最大 HP(u16 LE) |
| 0x14–0x15 | 經驗值(u16 LE) |
| 0x16 | 等級 |
| 0x17 之後 | 裝備欄位,尚未對到物品表 —— 原樣保留,不硬取名字 |

欄位是靠**六名初始角色橫向對照**定出來的:性別欄只有兩種值而 Mariah 與 Jaana 是 0x0C;
職業欄是可讀字母;而**最大 HP 恰好等於等級 × 30**(Lv2→60、Lv3→90、Lv5→150),
16 名角色無一例外 —— 這條內部一致性是位移正確最有力的佐證,也是回歸測試的斷言。

## 為什麼要主動撞牆

位移算錯時,讀出來的仍然是「某個數字」,不會自己報錯。所以 `ParseSave` 在解完之後
會主動檢查日期、隊伍人數、地點編號是否落在合理範圍,對不上就直接失敗 ——
早點失敗比默默解出一份錯的存檔好。
