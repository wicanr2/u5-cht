## 1. 兩件事,不要混為一談

「能看多遠」與「牆擋不擋得住」在原版是**分開**的兩層:

```
sub_29304  時鐘每分鐘跑一次 → 算出 byte_3E0B5(玩家的平方半徑)

sub_2E21C  掃出場景裡的光源,每個各跑一次半徑² 10 的 flood fill
             → byte_3F8F4 亮度圖(32×32,0 = 暗)

sub_29D64  每次重畫畫面
             ↓  地點 ≥ 0x80(戰鬥、四間石室)→ 整份複製,不做遮蔽
             ↓
sub_2E0E8(半徑, 玩家x−視窗x, 玩家y−視窗y)
             ↓  半徑 < 0 → 整張攤開(Wis An Ylem)
             ↓  半徑 = 0 → 整張全黑
             ↓
sub_2DDB0  以玩家為起點的 flood fill,查亮度圖,寫出 11×11 的罩子
```

⚠ **兩輪共用 `sub_2DDB0`,差別只在 `arg_C` 是不是 −0x6F**(見 §6)。
光源那一輪半徑是**上限**,玩家那一輪半徑是**捷徑** —— 抄成同一種必錯。

罩子**不是** 0/1 的可見遮罩,而是「這一格該畫什麼」:看得到就放地形碼,
看不到放 `0xFF`。`sub_2E0E8` 收尾時把值為 0 的格子 `dec` 成 `0xFF`——
兩種「看不見」(牆擋住、沒照到光)就此併成同一個值。

## 2. 距離表就是 dx² + dy²

`sub_2E8D0(x, y)` = `byte_601F0[y*11 + x]`。dump 出 121 個位元組後逐格核對:

```
50 41 34 29 26 25 26 29 34 41 50
41 32 25 20 17 16 17 20 25 32 41
34 25 18 13 10  9 10 13 18 25 34
29 20 13  8  5  4  5  8 13 20 29
26 17 10  5  2  1  2  5 10 17 26
25 16  9  4  1  0  1  4  9 16 25
                    ⋮(上下對稱)
```

角落 25+25 = 50、正上方 25、斜對角一格 2 —— **121 格全部等於 `dx²+dy²`**
(中心 (5,5))。所以引擎直接算,那張表只留在測試裡當 oracle
(`TestSightDistanceIsSquaredEuclidean`)。

全程用**平方**距離,沒有開根號。這一點會咬人:「相鄰」在斜角是 2 不是 1,
所以下一節那五個「貼著才透」的地形,斜著站就看不進去了。

## 3. 什麼擋視線(`sub_2E1D0`)

回傳 **1 = 穿得過**,0 = 擋住。兩段:

**貼著才看得穿的五個**(平方距離必須恰好是 1,也就是正上下左右一格):

```
4A 4B      門
BA BB 98   窗與魔法門
```

**永遠擋住的十九個**(`memchr(dword_601D0, 地形, 0x13)`):

```
09 0A 0C 0D   山與丘
4D 4E 4F      樹與牆
5A 97
B8 B9 BC      門(關著的)
D0 D1 D2 D3
F8 FE FF
```

其餘一律穿得過。兩張清單沒有交集(`TestDoorsAndBlockersDoNotOverlap` 釘住)。

## 4. flood fill(`sub_2DDB0`)

```
罩子 11 列 × 32 列距,初值全 0xFF
中心 (5,5) 先填上腳下的地形並入列
while 佇列非空:
    取出一格 (fx, fy)
    繞八鄰,順序是 W → SW → S → SE → E → NE → N → NW
        出界 → 跳過
        那一格不是 0xFF(走過了)→ 跳過
        平方距離 ≤ 半徑²  → 寫地形(捷徑,不做視線判定)
        sentinel == 0     → **不寫**,並當成 0xFF(光源那一輪:照不到,傳播打住)
        穿不過去          → 三個條件都成立才讓那面牆露出來:
                              來源那一格不是 0(不是黑的)
                              來源亮著
                              自己也亮著
                            否則寫 0xFF
        穿得過            → 亮著就寫地形,否則寫 0(黑)
        這一格的地形穿得過視線 → 入列
```

「亮著」查的是 `byte_3F8F4` —— **亮度圖**,不是場景圖。這是最容易讀錯的一處,
理由與後果見 §6。

四個細節值得記下來,因為都很容易在重寫時走樣:

**八鄰的順序不是查表來的。** 原版讓 `esi`/`edi` 一路累加,`dir` 從 7 遞減到 0,
一圈走完剛好繞回起點附近:

| dir | 7 | 6 | 5 | 4 | 3 | 2 | 1 | 0 |
|---|---|---|---|---|---|---|---|---|
| 動作 | x−1 | y+1 | x+1 | x+1 | y−1 | y−1 | x−1 | x−1 |
| 到達 | W | SW | S | SE | E | NE | N | NW |

攤成八組絕對偏移是等價的,但**順序不能換** —— 它決定了同一格被兩條路徑
照到時誰先寫進去。

**「走過了」用的是罩子本身,不是另一份走訪表。** 被判成看不見的牆維持
`0xFF`,所以**還會被別的方向再判一次**。這不是疏漏:同一面牆從亮的那側
看得到、從暗的那側看不到,靠的就是這個重判。改成走訪表的話,牆的可見與否
會變成「BFS 先從哪一側碰到它」——畫面上只會看到牆偶爾閃一下,極難追。
收斂靠的是「擋視線的格子不入列」,不是走訪表。

**演算過程中 0 與 0xFF 是兩個不同的值。** 牆要不要露出來,判的是來源那一格
「是不是 0」(`cmp byte[edx+eax], 0`)。用 0xFF 去比會整個反過來。
跑完之後才併。

## 5. 日照半徑(`sub_29304` 的 `loc_29463`)

```
if (半徑 >= 0x33) return;                      // 防呆,實際上沒有東西寫得到 51
舊值 = 半徑;
if (地點 == 25 || 樓層 < 0 || 時 < 5 || 時 > 19)
        半徑 = 2;                              // 夜、地下、亞拉臘號殘骸
else if (時 == 5)   半徑 = 漸變[分 / 10];       // 日出
else if (時 == 19)  半徑 = 漸變[(59 − 分) / 10]; // 日落
else                半徑 = 0x32;               // 白天
if (In Lor 還亮著 && 半徑 < 0x12) 半徑 = 0x12;
if (火把 還亮著   && 半徑 < 0x0A) 半徑 = 0x0A;
if (半徑 != 舊值) 下一幀重算罩子;
```

**日出漸變表 `byte_5FF5C`:IDA 把它的尾巴誤判成指標。** `.asm` 裡長這樣:

```
byte_5FF5C      db 2
                db 5, 0Ah, 14h
                dd offset unk_3122       ← 這其實是表的後兩個位元組
```

照 `.asm` 抄只會拿到四個(2 5 10 20),而索引是 `分/10`,跑到 0..5。
直接讀執行檔位元組才看得到完整的六個:

```
位移 0x5FF5C + 0x200:  02 05 0A 14 22 31 00 00
                                          ↑ 表在這裡結束
```

= 2, 5, 10, 20, 34, 49。從夜間亮度一路開到接近白天,十分鐘一階。

**兩個下限的大小關係是反直覺的**:In Lor 給 0x12 = 18,火把只給 0x0A = 10。
咒語比火把亮。而且兩個都是「不足才補」,不是相加 —— 同時有咒語與火把時,
火把那一關會因為半徑已達 18 而被跳過。

**0x32 = 50 正好等於視窗角落的平方距離。** 也就是說白天的半徑剛好蓋滿整個
11×11。這兩個數字來自完全不同的地方(日照表 vs 距離表),對得上不是巧合,
`TestDaylightCoversTheWholeWindow` 把它們釘在一起。

地點 25 是**亞拉臘號**(ARARAT)的殘骸 —— 整個地點寫死走夜間亮度。

## 6. 場景照明(`sub_2E21C`)—— 夜晚變暗的真正機制

只讀 `sub_2E0E8` + `sub_2DDB0` 會得到一個**錯誤**的結論。我第一版就是這樣:

> 半徑不參與傳播,而場景內的判定另有一條繞過半徑的路 ——
> 所以夜晚與白天畫面相同。

寫成測試後對不上直覺,回頭把 `sub_2E21C` 讀完才發現問題出在**同一個緩衝區
被兩支函式用作不同語意**:

| | `byte_3F8F4` 是什麼 |
|---|---|
| 我以為 | 場景地圖的複本 → `!= 0` 代表「這一格在場景範圍內」 |
| 實際上 | **亮度圖** → `!= 0` 代表「這一格被光照到」 |

`sub_2E21C` 的三段:

```
1. byte_3F8F4[0..0x3FF] 全部填 0xFF
2. 掃過以視窗左上角為原點的 32×32:
     memchr(dword_601E4, 地形, 0x0A) 命中 → 記下座標,並把地形寫進亮度圖
3. 對每一個光源:
     清空 byte_3F6E4 的 11 列當走訪表
     sub_2DDB0(0x0A, ly−5, lx−5, ly−5, lx−5, 0x20, byte_3F8F4)
                ↑半徑²    ↑來源位移    ↑目的位移        ↑寫進亮度圖
4. 收尾:亮度圖裡還是 0xFF 的格子 inc 成 0(= 沒照到)
```

★ **第 3 步的 `arg_C` 不是 −0x6F** —— 所以 `sentinel = 0`,走的是
`sub_2DDB0` 裡我原本判定為死碼的那條分支。那條分支的關鍵差別:

```
loc_2E074:  var_41D = 0xFF        ; 超出半徑 → 連寫都不寫
```

`0xFF` 在擋視線清單裡 → 不入列 → **傳播停在半徑上**。
也就是說:光源那一輪的半徑**是上限**,玩家那一輪的半徑**是捷徑**。
同一支函式,一個旗標,兩種語意。

拼起來之後整條線就通了:

- **白天**:玩家半徑² 50 蓋滿整個 11×11 → 捷徑處理一切,亮度圖用不上。
- **夜裡**:玩家半徑² 2 只剩自己加八鄰(平方距離 ≤ 2 剛好是 3×3);
  再遠的東西要**亮度圖說它亮**才看得見 —— 那就得有火盆或營火照著。
- **火把 / In Lor**:把玩家半徑² 抬到 10 / 18,那一圈直接放大。
- **光源照不進隔壁房間**:光源那一輪同樣被牆擋住。

十種發光地形(`dword_601E4`,後面接 0 收尾):

```
DC        月門(`sub_DEE4` 畫進場景時就是這個碼)
BD BE BF  火盆
B0 B1 B2 B3
DE        營火
BC        ★ 同時也在擋視線清單裡 —— 牆上帶火的窗:擋住視線,但照亮四周
```

兩張表的交集只有 `BC` 一個。

### 教訓

**只讀一支函式就替一個共用緩衝區定語意,一定會推錯。** `byte_3F8F4` 在
`sub_2DDB0` 裡只被讀、沒被寫,而讀的位置又剛好與「場景座標」對得起來,
所以「它是場景圖」看起來完全講得通 —— 直到把寫它的那一支也讀完為止。
判斷方式:**先找出誰寫它**(`sub_2E21C` 是唯一的寫入者),再談它是什麼。
這與 `rulebook/62` 是同一件事,只是對象從「值」換成「緩衝區」。

## 7. `sub_2E944` 其實是**燈塔的光束**

我原本把它記成「光源的閃爍動畫」。追下去才發現不是:

```
sub_10738   memchr(byte_404F4, 0x1B, 0x400)     ← 在世界地圖的 32×32 視窗裡找 tile 0x1B
              找到 → word_4140C = x, word_4140E = y
sub_2E944   每幀:關掉扇區 n、打開扇區 n+2,n 加一,到 16 歸零
sub_2E8E8   把某個扇區的 16 個格子在**亮度圖**上設成 0xFF(或 0)
```

`0x4120C` 那張表不是同心圓,是**十六個扇區排成羅盤**:
1 = 正北、5 = 正東、9 = 正南、13 = 正西,順時針。三個扇區同時亮
(`sub_2E944` 開頭點 0/1/2),所以是一道**掃過去的光束**。

★ **tile 0x1B = 燈塔**,而且對得上:`BRIT.DAT` 裡 0x1B **剛好出現 4 次**
—— 破霧塔 / 風暴鴉 / 灰港 / 浪導四座;`UNDER.DAT` 與四個場景檔一次都沒有。
(`docs/re/03` 當初是從四座燈塔的座標反推出 tile 27 = 0x1B 的,兩邊獨立對上。)

⚠ 這也修正了我實作時的第一個版本:我寫成「找**場景**裡的燈塔」,
那樣永遠找不到 —— 燈塔是**大地圖**上的地形,場景檔裡根本沒有這個碼。

⚠ 而且它寫的是**亮度圖**不是罩子 —— 光束掃到哪裡,哪裡才真的看得見,
不只是畫面上亮一下。這就是為什麼原版每掃一格都要設 `byte_4198A = 1`
逼視線遮蔽重算。

另外原版把亮度圖當**快取**(只有 `sub_2E21C` 被呼叫時才重建,共 8 個呼叫點);
本移植是每幀重算。結果一樣,只是多花一點 CPU(32×32 掃描 + 每個光源一次
121 格的 flood fill),在 CPU 繪製路徑上量不到。

## 8. 哪些場合不做遮蔽

`sub_29D64` 在 `cmp byte_3E0A3, 80h; jnb loc_29EB4` 分岔:地點編號 ≥ 0x80
直接把場景視窗整份 `rep movsd` 過去,**不跑 flood fill**。也就是:

- **戰鬥**:11×11 的戰場正好等於視窗,全畫。
- **四間石室**(聖壇、寶典、審問、王座廳):地點編號是 `0xFF`。
- **地牢**是另一套(第一人稱透視),不走這條路。

`internal/game/sight.go` 的 `SightMask()` 在這三種情形回 `nil`,呼叫端照常全畫。

## 9. 順帶修掉的一個測試陷阱

`internal/game` 的測試輔助 `walkable()` 原本從 0 開始找「通行表允許行走」的
地形,而 **0 就是它回傳的第一個值**。但 0 在罩子裡是「看不見」——
`sub_2E0E8` 收尾時把 0 一律併成 0xFF,地形碼真的是 0 的格子也一起被併掉
(原版如此,照抄)。

結果是所有用合成場景的測試都跑在一整片「地形碼 0」的地圖上。移動規則照樣
驗得過(那些規則不看這件事),但任何與可見度有關的測試都會全黑,而且看不出
原因 —— 我第一版的視線測試就是這樣全掛的。`walkable()` 現在從 1 開始找。
