## 1. 兩件事,不要混為一談

「能看多遠」與「牆擋不擋得住」在原版是**分開**的兩層:

```
sub_29304  時鐘每分鐘跑一次 → 算出 byte_3E0B5(平方半徑)
             ↓
sub_29D64  每次重畫畫面
             ↓  地點 ≥ 0x80(戰鬥、四間石室)→ 整份複製,不做遮蔽
             ↓
sub_2E0E8(半徑, 玩家x−視窗x, 玩家y−視窗y)
             ↓  半徑 < 0 → 整張攤開(Wis An Ylem)
             ↓  半徑 = 0 → 整張全黑
             ↓
sub_2DDB0  以玩家為起點的佇列式 flood fill,寫出 11×11 的罩子
```

罩子**不是** 0/1 的可見遮罩,而是「這一格該畫什麼」:看得到就放地形碼,
看不到放 `0xFF`。`sub_2E0E8` 收尾時把值為 0 的格子 `dec` 成 `0xFF`——
兩種「看不見」(牆後、場景外)就此併成同一個值。

## 2. 距離表就是 dx² + dy²

`sub_2E8D0(x, y)` = `byte_601F0[y*11 + x]`。dump 出 121 個位元組後逐格核對:

```
50 41 34 29 26 25 26 29 34 41 50
41 32 25 20 17 16 17 20 25 32 41
34 25 18 13 10  9 10 13 18 25 34
29 20 13  8  5  4  5  8 13 20 29
26 17 10  5  2  1  2  5 10 17 26
25 16  9  4  1  0  1  4  9 16 25
                    ⋮(上下對稱)
```

角落 25+25 = 50、正上方 25、斜對角一格 2 —— **121 格全部等於 `dx²+dy²`**
(中心 (5,5))。所以引擎直接算,那張表只留在測試裡當 oracle
(`TestSightDistanceIsSquaredEuclidean`)。

全程用**平方**距離,沒有開根號。這一點會咬人:「相鄰」在斜角是 2 不是 1,
所以下一節那五個「貼著才透」的地形,斜著站就看不進去了。

## 3. 什麼擋視線(`sub_2E1D0`)

回傳 **1 = 穿得過**,0 = 擋住。兩段:

**貼著才看得穿的五個**(平方距離必須恰好是 1,也就是正上下左右一格):

```
4A 4B      門
BA BB 98   窗與魔法門
```

**永遠擋住的十九個**(`memchr(dword_601D0, 地形, 0x13)`):

```
09 0A 0C 0D   山與丘
4D 4E 4F      樹與牆
5A 97
B8 B9 BC      門(關著的)
D0 D1 D2 D3
F8 FE FF
```

其餘一律穿得過。兩張清單沒有交集(`TestDoorsAndBlockersDoNotOverlap` 釘住)。

## 4. flood fill(`sub_2DDB0`)

```
罩子 11 列 × 32 列距,初值全 0xFF
中心 (5,5) 先填上腳下的地形並入列
while 佇列非空:
    取出一格 (fx, fy)
    繞八鄰,順序是 W → SW → S → SE → E → NE → N → NW
        出界 → 跳過
        那一格不是 0xFF(走過了)→ 跳過
        平方距離 ≤ 半徑²  → 寫地形(捷徑,不做視線判定)
        穿不過去          → 三個條件都成立才讓那面牆露出來:
                              來源那一格不是 0(不是黑的)
                              來源在場景內
                              自己也在場景內
                            否則寫 0xFF
        穿得過            → 在場景內寫地形,否則寫 0(黑)
        這一格的地形穿得過視線 → 入列
```

三個細節值得記下來,因為都很容易在重寫時走樣:

**八鄰的順序不是查表來的。** 原版讓 `esi`/`edi` 一路累加,`dir` 從 7 遞減到 0,
一圈走完剛好繞回起點附近:

| dir | 7 | 6 | 5 | 4 | 3 | 2 | 1 | 0 |
|---|---|---|---|---|---|---|---|---|
| 動作 | x−1 | y+1 | x+1 | x+1 | y−1 | y−1 | x−1 | x−1 |
| 到達 | W | SW | S | SE | E | NE | N | NW |

攤成八組絕對偏移是等價的,但**順序不能換** —— 它決定了同一格被兩條路徑
照到時誰先寫進去。

**「走過了」用的是罩子本身,不是另一份走訪表。** 被判成看不見的牆維持
`0xFF`,所以**還會被別的方向再判一次**。這不是疏漏:同一面牆從亮的那側
看得到、從暗的那側看不到,靠的就是這個重判。改成走訪表的話,牆的可見與否
會變成「BFS 先從哪一側碰到它」——畫面上只會看到牆偶爾閃一下,極難追。
收斂靠的是「擋視線的格子不入列」,不是走訪表。

**演算過程中 0 與 0xFF 是兩個不同的值。** 牆要不要露出來,判的是來源那一格
「是不是 0」(`cmp byte[edx+eax], 0`)。用 0xFF 去比會整個反過來。
跑完之後才併。

## 5. 日照半徑(`sub_29304` 的 `loc_29463`)

```
if (半徑 >= 0x33) return;                      // 防呆,實際上沒有東西寫得到 51
舊值 = 半徑;
if (地點 == 25 || 樓層 < 0 || 時 < 5 || 時 > 19)
        半徑 = 2;                              // 夜、地下、亞拉臘號殘骸
else if (時 == 5)   半徑 = 漸變[分 / 10];       // 日出
else if (時 == 19)  半徑 = 漸變[(59 − 分) / 10]; // 日落
else                半徑 = 0x32;               // 白天
if (In Lor 還亮著 && 半徑 < 0x12) 半徑 = 0x12;
if (火把 還亮著   && 半徑 < 0x0A) 半徑 = 0x0A;
if (半徑 != 舊值) 下一幀重算罩子;
```

**日出漸變表 `byte_5FF5C`:IDA 把它的尾巴誤判成指標。** `.asm` 裡長這樣:

```
byte_5FF5C      db 2
                db 5, 0Ah, 14h
                dd offset unk_3122       ← 這其實是表的後兩個位元組
```

照 `.asm` 抄只會拿到四個(2 5 10 20),而索引是 `分/10`,跑到 0..5。
直接讀執行檔位元組才看得到完整的六個:

```
位移 0x5FF5C + 0x200:  02 05 0A 14 22 31 00 00
                                          ↑ 表在這裡結束
```

= 2, 5, 10, 20, 34, 49。從夜間亮度一路開到接近白天,十分鐘一階。

**兩個下限的大小關係是反直覺的**:In Lor 給 0x12 = 18,火把只給 0x0A = 10。
咒語比火把亮。而且兩個都是「不足才補」,不是相加 —— 同時有咒語與火把時,
火把那一關會因為半徑已達 18 而被跳過。

**0x32 = 50 正好等於視窗角落的平方距離。** 也就是說白天的半徑剛好蓋滿整個
11×11。這兩個數字來自完全不同的地方(日照表 vs 距離表),對得上不是巧合,
`TestDaylightCoversTheWholeWindow` 把它們釘在一起。

地點 25 是**亞拉臘號**(ARARAT)的殘骸 —— 整個地點寫死走夜間亮度。

## 6. ⚠ 一個與直覺相反、尚未對原版實測的結論

**半徑不參與傳播。** `sub_2DDB0` 要不要往外傳,只看地形擋不擋視線
(`sub_2E1D0`),與 `arg_0` 無關。而且**場景內的判定另有一條繞過半徑的路**:
穿得過的地形只要在場景內就顯示(`loc_2E031` → `loc_2E065`),
擋視線的地形只要來源不是黑的、兩格都在場景內就顯示(`loc_2E025` 的三個條件)。

推論:**在資料完整的場景裡,半徑對可見度沒有影響 —— 夜晚與白天畫面相同。**
實測本引擎的移植版,一間 5×5 的房間在 12 時與 0 時的罩子完全一樣。

我原本寫的測試假設「夜裡看得到的格數會變少」,對不上之後回去讀組語才發現
上面這件事。這一段是照組語寫的,不是照印象寫的。

**但這件事還沒有對 DOSBox 原版實測比對。** 三種可能:

1. 原版就是如此(U5 的夜晚靠的是牆變不透明,而房間本來就有牆圍著);
2. 變暗發生在**繪製層**而不是罩子(`sub_29BEC`),是調色盤或亮度而非隱藏;
3. FM Towns 版與 DOS 版在這裡不同。

在跑過對照之前,**不宣稱「夜間效果已完成」**(`rulebook/65`:驗收標準是
對 reference 實測,不是自家測試綠)。目前釘住的是「程式碼確實如此」。

## 7. 還沒做:場景光源各自的 flood fill(`sub_2E21C`)

`sub_2E21C` 掃過整張 32×32,用 `memchr(dword_601E4, 地形, 0x0A)` 找出
**十種會發光的地形**(火把、營火之類),把座標記下來,然後**為每一個光源
各跑一次 flood fill**,結果疊進罩子。這是「牆上的火把照亮房間」的效果。

`sub_2E944` 是它的動畫:`byte_41414` 是 0..15 的計數器,每幀讓光源周圍的
環閃一下,並設 `byte_4198A = 1` 逼罩子重算。

兩支都還沒移植。少了它們,有光源的房間會比原版暗一點 —— 但因為 §6 的關係,
目前的實作在場景內本來就不會暗,所以看不出差別。**這兩件事要一起做**:
先確認 §6 的疑問,再決定光源疊加該長什麼樣。

## 8. 哪些場合不做遮蔽

`sub_29D64` 在 `cmp byte_3E0A3, 80h; jnb loc_29EB4` 分岔:地點編號 ≥ 0x80
直接把場景視窗整份 `rep movsd` 過去,**不跑 flood fill**。也就是:

- **戰鬥**:11×11 的戰場正好等於視窗,全畫。
- **四間石室**(聖壇、寶典、審問、王座廳):地點編號是 `0xFF`。
- **地牢**是另一套(第一人稱透視),不走這條路。

`internal/game/sight.go` 的 `SightMask()` 在這三種情形回 `nil`,呼叫端照常全畫。

## 9. 順帶修掉的一個測試陷阱

`internal/game` 的測試輔助 `walkable()` 原本從 0 開始找「通行表允許行走」的
地形,而 **0 就是它回傳的第一個值**。但 0 在引擎裡是「這一格沒有資料」的
哨兵:場景緩衝判在不在場景內看的就是它是不是 0,罩子最後也把 0 併成
「看不見」。

結果是所有用合成場景的測試都跑在一整片「沒有資料」的地圖上。移動規則照樣
驗得過(那些規則不看這一格),但任何與可見度有關的測試都會全黑,而且看不出
原因 —— 我第一版的視線測試就是這樣全掛的。`walkable()` 現在從 1 開始找。
