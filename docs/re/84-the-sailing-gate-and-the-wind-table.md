## 0. 為什麼一定要用 IDA 的 xref 而不是讀 `.asm`

兩個問題都是「**誰在寫這塊記憶體**」:

- 誰寫隊伍座標 `byte_3E0A6` / `byte_3E0A7`?(航行)
- 誰寫物件槽的 `+2` / `+3`?(怪物移動)

物件座標的存取寫成 `byte ptr dword_3E46C+2[edx*8]` —— **32 個槽共用一個符號名,
槽號在暫存器裡**。grep `.asm` 找不到「第 7 槽的 Y」,而 xref 圖知道每一筆參考
落在哪個位址、是讀還是寫。`CLAUDE.md §4.5` 早就寫了這條,這次是它真正兌現。

⚠ **踩到 §4.5 記的那個陷阱**:第一次跑 IDC 得到
`Failed to initialize IDA as library (error code 1)`,看起來像 image 壞了。
正對照(拿已知可用的 `ida_xref.idc` 跑同一個庫)也失敗 ⇒ 問題不在腳本。
真正的原因是**檔案在 `re_work/fmtowns/` 而工作目錄是 `re_work/`** ——
IDA 開不到輸入檔,而它的錯誤訊息完全沒提這件事。
⇒ 正確用法:`tools/ida.sh idc fmtowns/WORRIORS.EXP.i64 <script>.idc`。

## 1. ★★ 怪物移動找到了:`sub_2D38` → `sub_2B24`

`docs/re/83` 說「怪物移動全檔找不到」—— 因為我**沒讀完 `sub_2D38` 的尾巴**:

```asm
loc_2E11:  push  1
loc_2E13:  push  edi            ; 槽號
           call  sub_2B24       ; ★★ 這才是移動
loc_2E1C:  retn                 ; ← 這條路徑不移動
```

`sub_2B24(槽, 旗標)` 算出物件到隊伍的**帶號環繞** dx/dy,再導出一格的步向
(−1 / 0 / +1)⇒ **它是「往隊伍走一格」**。所以:

```
sub_2E24 → sub_2D38(槽) → 閘門 → sub_2B24(槽, 1)   ; 追著隊伍走
                        → 漩渦那條 → sub_2A54(槽)   ; ★ 隨機遊走(擲 4 向,最多試 3 次)
```

### ⚠ 於是 `docs/re/83` §2 的「動 / 不動」標反了

`loc_2E11` 是**移動**、`loc_2E1C` 是**跳過**。重新讀敵船那一段:

```
if (byte_3E0A2 == 0) → 跳過                 ; 無風 → 敵船不動
延遲 = dword_4FD50[(kind−0x2C)*4 + 風向]
if (延遲 == 4) → 移動                        ; ★★ 4 = **全速**,不是動不了
物件[槽][7]++
if (物件[槽][7] <= 延遲) → 移動
物件[槽][7] = 0; → 跳過                      ; 超過才跳一回合
```

⇒ **數字越大越快**,不是「延遲」。敵船每 `延遲+1` 回合跳一次:
延遲 2 → 走 2 跳 1(2/3 的回合會動)、延遲 3 → 3/4、**延遲 4 → 每回合都動**。

而那張表每個朝向都有**兩個 4** ⇒ 敵船從來不會被風向困住,只是慢一點。
這對敵船很合理 —— 否則牠們會變成靶子。

## 2. ★★ 玩家的航行閘門:`sub_2CCFC` 的最後五行

```asm
loc_2CE50:                          ; 想去的方向就是現在的船頭(不需轉向)
    cmp  byte_3E08C, 24h
    jnb  short loc_2CE67            ; ★ >= 0x24(收帆的大船)→ 回 0 = 照走
    cmp  byte_3E0A2, 0
    jnz  short loc_2CE67            ; ★ 有風 → 回 0 = 照走
    mov  ebx, 1                     ; ★ 揚帆(0x20..0x23)且**完全無風** → 回 1 = 動不了
loc_2CE67:
    mov  eax, ebx
    retn
```

⇒ **玩家的航行只有一條閘門:揚著帆而且風是 0(Calm)時走不了。**
**有風就照走,不管風向。**

而 `sub_2CCFC` 回 1 的另一種情況是「**想去的方向不是船頭**」—— 那時它只轉向
(`byte_3E08C = (舊 & 0xFC) + 方向`)並印 `"Head <方向>"`,這一步就用掉了。
引擎的 `turnShipInstead` 已經對上這一半。

### 風向真正的作用在 `sub_2D2D0`,而且不是「能不能走」

揚帆時 `sub_2D9D0` 會先跑 `sub_2D2D0`(line 79860,比移動 `sub_2D174` 還早),
那是一個**燒時間**的迴圈:

```
n = 1 + (帆向與風向不同的分量數)      ; 1 同向 / 2 反向 / 3 垂直
跑 (n % 3) 次:{ 推時鐘;(條件符合時)跑一個世界回合;重畫 }
```

⇒ **同向 1 次、反向 2 次、垂直 0 次。** 它加的是**時間與世界回合**(怪物的行動
機會),不是位移。⇒ 逆風的代價是「同一步花兩倍時間、怪多走一輪」,
而不是「走不動」。

⚠ 這一段引擎完全沒有。⬜ 列進 `WORKLIST`。

## 3. ★★★ 風向表:三個獨立來源一致,而引擎抄反了

### 三個來源

**(a) 原版自己印的名字**(`sub_2A984` 的 `jpt_2A9E4`):

```
case 0 "Calm"   case 1 "North"   case 2 "South"   case 3 "East"   case 4 "West"
```

**(b) 向量表**(`byte_601C7` = X、`byte_601CB` = Y;`0xFF` 就是 −1)。
逐位元組展開 `0x601C7..0x601CF` = `00 00 00 FF 01 | 01 FF 00 00`:

| 風值 | X | Y | 推向 |
|---|---|---|---|
| 1 | 0 | +1 | 南 |
| 2 | 0 | −1 | 北 |
| 3 | −1 | 0 | 西 |
| 4 | +1 | 0 | 東 |

哪一張是 X 哪一張是 Y,由 `sub_2D174` 的方向編碼定案:它的 case 3 做 `ebx--`
並呼叫 `sub_2CCFC(0)`(= North),case 4 做 `ebx++` 並呼叫 `sub_2CCFC(2)`(= South)
⇒ **`ebx` 是 Y**;而 `sub_2D2D0` 用 `var_4` 接 case 1/2、`ebx` 接 case 3/4
⇒ **`var_4` 是 X**,而它對的是 `byte_601C7`。

**(c) Rel Hur 的方向 → 風值**(`sub_1CDA4` 的 `jpt_1CDD0`):

```
方向鍵 1(西)→ 風 4      方向鍵 2(東)→ 風 3
方向鍵 3(北)→ 風 1      方向鍵 4(南)→ 風 2      0 → 風 0
```

### 結論:名字 = 從哪來,向量 = 推向哪

| 風值 | 原版名 | 推向 | 中文 |
|---|---|---|---|
| 1 | North | 南 | 北風 |
| 2 | South | 北 | 南風 |
| **3** | **East** | 西 | 東風 |
| **4** | **West** | 東 | 西風 |

「北風把你往南推」—— 氣象學上正確,而三個來源逐一相符。

### ⇒ 引擎的兩個錯

1. **`WindWest = 3` / `WindEast = 4` 對調了**(原版 3 = East、4 = West)。
   ⇒ 狀態列顯示的風向名一直是錯的,而 Rel Hur 的「西 → 3」也跟著錯。
2. **`WindDelta` 的南北反了**:引擎 `WindNorth → (0,−1)`(往北推),
   原版是 `(0,+1)`(往南推)。東西那兩個**向量剛好對**,因為兩個錯互相抵消
   (引擎把 3 叫西風並給 `(−1,0)`;原版把 3 叫 East 也給 `(−1,0)`)。

⚠ `u5data/wind.go` 原本的註解寫「方向是從 `sub_2D2D0` 讀出來的:風 1 → dy = −1 北」
—— **X 與 Y 認錯了,而且沒有拿印出來的名字交叉檢查**。
教訓:**一張「值 → 方向」的表至少要兩個來源才敢定案**;這次有三個。
