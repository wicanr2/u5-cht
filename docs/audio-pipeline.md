## 1. 已經打通的部分(可重跑)

### 1.1 場景 → 曲號 → 檔名

原版把「播第幾首」寫在程式碼裡(32 個 `sub_3181C(n)` 呼叫點 + `sub_31DC0`
的地點跳表),**不在任何資料表裡** —— `U5_BGM.TBL` 只給檔名與六聲道音量。
完整推導與 32 個呼叫點見 `docs/re/87`。

引擎接了八個換曲點:進場景 7、離場地表 1 / **幽冥界 0x0A**、進地牢 9、
離開地牢 1、月門 1、開戰 3、勝利 0、上船 / 上小艇 2。

```
internal/game/music.go       曲號常數 + playSong + overworldSong
internal/u5data/bgm.go       U5_BGM.TBL + StartupSong(sub_31DC0)
internal/audio/audio.go      曲號 → 檔名 → 後端
```

⚠ 曲號 **0 是勝利那一首**,所以 `State.song` 刻意不匯出(零值陷阱,見 `docs/re/87` §7)。

### 1.2 兩條 CDDA

```bash
tools/cdda2ogg.sh            # 預設輸出 assets/audio/
```

CDDA 是紅皮書規格:44,100 Hz、16-bit、立體聲、LE、**176,400 byte/s**
⇒ 長度可以從位元組數算出來當驗收,不必猜:

| 音軌 | 位元組 | 算出來 | 轉出的 ogg |
|---|---|---|---|
| Track 2 | 31,752,000 | 180 s | ✅ 180 s |
| Track 3 | 65,444,400 | 371 s | ✅ 371 s |

腳本在除不盡 176,400 時會出聲警告(那表示不是純 CDDA 或抽檔抽錯),
並在轉完之後用 `ffprobe` 比長度,差超過 1 秒就失敗。

⬜ **誰在什麼時候播它們還沒追。** 但 `cdr_mtplay` / `cdr_rmtplay` 那組
CD-ROM 音軌 API **確實連進了執行檔**(`docs/re/89` §3a)⇒ 不是裝飾。

### 1.3 `.EUP` 與 `.FMB` 的解碼

事件模型 §3.2、時間 §3.3、速度 §3.4、音色參數佈局 §3.1。

## 2. 為什麼不能沿用 u1-cht 的渲染器

`../u1-cht/tools/render_eup_music.py` 是**自製 2-op FM 近似**:音序照讀,
但**音色是自己編的**。當初那是唯一的路,因為不知道原版音色在哪。

現在知道 `FM_BANK.FMB` 就在光碟上,而且參數佈局已定案(§3.1)。
`CLAUDE.md §3.0` 的鐵則是「素材全部從原版媒體抽取解碼,不自製」——
明知有原版音色卻用自編的,就是違反它。

⚠ 分清兩件事:**合成器(程式)是我們寫的,音色(資料)必須是原版的。**
寫一個 4-op FM 合成器不違反 §3.0;編一組音色參數才違反。

⚠ 而且那份渲染器的 **tick 常數對 U5 是錯的**(0.0108 vs 正確的 0.00694,
差 1.56 倍,見 §3.4),相位掃描判準也會停在錯的地方(§3.2)。

## 3. ✅ 硬結解開了(使用者選路線 2:外部格式文件 + 一手否證)

`docs/re/89` 定位出「原版的解析在 `TBIOS.BIN` 裡,不在遊戲執行檔」。
使用者選擇**依外部 EUPHONY / FMB 格式文件實作**。實際做的時候多加了一層
**用一手資料否證**,結果兩個來源互相確認 —— 比單靠文件強得多。

### 3.1 `.FMB` 音色參數(佈局)

```
+0..+7          名字 8 byte
+8 +9 +10 +11   DT/MUL    運算子 0..3
+12..+15        TL
+16..+19        KS/AR
+20..+23        DR
+24..+27        SR
+28..+31        SL/RR
+32             FB/ALG
+33             L/R + AMS/PMS
+34..+47        全 0
```

- **來源一(一手否證)**:YM2612 各欄位的位元寬度是已知的 ⇒ 任何候選佈局只要
  有一格超出對應欄位上限就是錯的。掃全部 126 個有名字的音色,每組都剛好塞進去,
  而**互換就爆掉**(`KS/AR` 上限 223、`SL/RR` 上限 255 都放不進 `TL` 或 `SR`)。
  兩格幾乎是簽名:**`+32` 實測 0..61 而 FB/ALG 寬度剛好 0..63**;
  **`+33` 全部 ≥ 192 ⇒ L/R 輸出位元永遠都開**。
- ★★ **最強的是跨欄位那條**:用 `+32` 的 ALG 挑出載波、再看 `+12..15` 的 TL,
  **126/126 個音色的載波最小 TL ≤ 15**。它同時用到兩個位移,任一個錯就破。
- **來源二**:[`gzaffin/eupmini`](https://github.com/gzaffin/eupmini) 的
  `setInstrumentParameter` 逐行讀 `instrument[8] [12] [16] [20] [24] [28] [32]`,
  運算子以 `instrument + n` 取偏移 ⇒ **完全吻合**。它也記載「FMB 剛好 6,152 byte」。

### 3.2 `.EUP` 事件模型(★ 第一版讀錯,已更正)

**一個音符是 12 byte**:`0x9n` 前半 + `0x8n` 後半,兩半的低 nibble 是同一個聲道。
一手證據是**零例外的配對**(882/882 雙向),以及 `[1]` 的鑑別力
(前半 100% 等於聲道、後半只有 0.7%)。

⚠ 第一版把 `0x8n` 當成 note-off,還拿「兩者筆數相等」當決定性證據 ——
**數字是真的,結論是錯的**。同一個觀察支持兩個不同的模型;
要用**能區分它們**的檢查(這裡是 `[1]`)。

### 3.3 時間:小節內的 tick

`0xF2` 是小節結束、時間欄固定 **384 = 96 ppqn × 4/4**;所有音符的小節內 tick
都 < 384(最大 381),而且**每一小節內單調不遞減**(15 首、零例外)。

### 3.4 速度在 `簽章 + 15`

值 88 / 90 / 59 / 67,**有意義地變化且與曲子性格相符**(最慢的 59 也最長)。

```
每 tick 的秒數 = 60 / (96 × BPM)
曲長          = 小節數 × 384 × 每 tick 的秒數
```

十五首 11..297 秒、合計 **23.3 分鐘**。

⚠ `../u1-cht` 的渲染器用 **0.0108 s/tick**,那是從 U1 曲長**反推**的;
90 BPM 的正確值是 **0.00694 s** —— **差 1.56 倍**。拿反推的常數渲染 U5 會慢 56%。

### 3.5 仍然未定的三件小事(不擋渲染)

- ⬜ 音符**後半那 5 個位元組**的語意(`[1]` 疑為音長)⇒ 音長要另找依據,
  或先用「到同聲道下一個音符為止」。
- ⬜ `M4.EUP` 的**聲道 4 有音符卻沒有 program change** ⇒ 渲染器要有明確的
  預設音色行為,而那個行為目前沒有依據。
- ⬜ `簽章 + 14`(十四首 51、`M92` 112)、每首固定 130 筆的 `0x00` 記錄。

## 4. 驗收條件(決定性,不是「跑得動」)

| # | 項目 | 驗收 |
|---|---|---|
| A1 | CDDA 轉檔 | ✅ 兩軌長度與位元組數算出來的秒數差 ≤ 1 s(腳本內建) |
| A2 | `.EUP` 事件模型 | ✅ 十五首都解得過(後半不是 `0x8n` 就報錯);音符聲道 0..5;小節內 tick < 384 且每小節單調 |
| A2b | 速度 | ✅ 十五首算出 11..297 s、合計 23.3 分鐘(判準:每首 5..400 s、合計 10..60 分鐘) |
| A3 | `.FMB` 佈局 | ✅ 8 + 128 × 48 整除;`TRUMP1` / `FLUTE` / `OBOE` 讀得出來 |
| A4 | 渲染器 | ⬜ 十五首都渲染成 ogg;**長度要與 §3.4 算出來的秒數相符**(這條現在是硬驗收,因為公式已定案) |
| A5 | 音色參數佈局 | ✅ 兩個獨立來源 + 跨欄位一致性(126/126) |
| A5b | 音色**聽起來**對 | ⬜ 需要對照來源;佈局對不代表我的合成器對 |
| A6 | 引擎換曲 | ⬜ 進城 / 開戰 / 上船 / 進地牢各切一次,曲號與檔案都對(曲號部分已有單元測試) |
| A7 | 不崩 | ⬜ 熱鍵切主題、快速進出場景不掉音、不卡住(u1-cht 踩過) |

⚠ A4 的「長度要能推算並相符」是刻意的:**不要用「聽起來對」當驗收** ——
tick 換算錯 20% 也還是「聽起來像」。
